## 1. 待拍板项 1：实现路径 —— 走 ②（已有桥接 + 脚本）还是走 ①（自写插件）

### 背景（这是什么 / 从哪来 / 影响什么）

DSH 有两种方式做「用户发言时自动注入一段提醒」：

- **② 用现成桥接 `dsh-hooks-claude-code`**：它挂在 DSH 的 `agent/pre-step` 事件上，把用户这一轮的话通过标准输入送给你写的一个脚本，脚本返回 JSON，桥接把其中 `additionalContext` 作为一条消息注入本轮。**你不需要写 DSH 插件，只写一个判断脚本 + 一份 hooks.json 配置。**
- **① 自写一个 Cordis 插件**：直接挂在 `agent/pre-step` 事件上，用 JS/TS 在进程内判断并注入。能力强（可读写进程内状态），但要写一个完整插件、处理构建/挂载/热更新，成本高。

### 关键区别

| 维度 | ② 桥接+脚本 | ① 自写插件 |
|---|---|---|
| 你要写什么 | 一个判断脚本（几十行 node）+ hooks.json | 完整插件 + 打包 + 挂载 |
| 能直接访问 DSH 进程内状态吗 | 不能，只能拿到桥接传给它的 payload（含用户这句话、会话语、工作目录） | 能 |
| 维护成本 | 低，逻辑全在一个独立脚本里 | 高，涉及插件生命周期 |
| 交接文档建议 | **建议 ②**（§5.3），理由是成本低、可快速验证 | — |

### 我的推荐

**走 ②**。理由：
1. 本需求只需要「读用户这一句话判断意图 + 输出一段静态提醒」，不需要任何进程内状态，① 的能力是多余且增加复杂度；
2. 桥接已核实存在，不用从零搭；
3. 交接文档 §5.3 也倾向 ②，并建议「验证有效后再考虑重写成 ①」——正合「先快后稳」的工程节奏。

请确认：**走 ②（推荐）/ 走 ① / 其他意见**。

## 2. 待拍板项 2：挂在哪个生效范围（profile）

### 背景

DSH 有多个 profile（`web`、`desktop`、`test` 等）。plugin 挂到哪个 profile 就只在那个 profile 的会话里生效。你日常用的是 `web` profile（`~/.dsh/profiles/web/`）。

### 选项与影响

- **只挂 `web`**（我的推荐）：改动最小、最容易验证（就是你日常的环境），验证通过后再扩到其他 profile。
- **挂全部**：要改多个 profile 的配置，且 desktop 等 profile 可能也装同款桥接，重复劳动。

请确认：**只挂 web（推荐）/ 挂其他**。

## 3. 待拍板项 3：触发判断策略（这是本需求难点，必须一起定）

### 背景

判断脚本要回答一个问题：**用户这句话是不是在「要我做决策 / 要我做审批」？** 只有命中才注入提醒。

- **写窄了会漏**：用户换个说法（「你看这个怎么弄」「给我个方案」「这个能行吗」）就不认了；
- **写宽了等于常驻**：每轮都注入，就丧失「只在需要时提醒、平常不加 token」的初衷。

交接文档 §5.1 列了 4 个可选思路。

### 可选思路（展开说明）

| 思路 | 是什么 | 优点 | 缺点 |
|---|---|---|---|
| A. 关键词/正则 | 用一组词语/模式（「方案」「怎么弄」「能行吗」「审批」「拍板」…）判断 | 极快、零成本、可本地确定性测试 | 脆弱，换说法就漏；太宽就跑偏 |
| B. 小模型分类 | 调一个小模型判断这句话算不算「要决策」 | 理解力强、换说法也认 | 每轮多一次调用，有延迟和 token 成本；还要配模型地址 |
| C. 混合（先正则粗筛，命中才调模型精判） | 正则先粗筛掉明显不相关的，候选的才交给模型 | 平衡省成本与准确率 | 实现最复杂，且本机/局域网模型现在仍有故障（交接 §7.4） |
| D. 不判意图，改为「固定注入」 | 每轮都注入，只是内容不判断 | 实现最简单 | 丧失省 token 的意义，每轮都多一段 |

### 关于「可靠」的现实边界（务必先看清，避免过度承诺）

验证集里能覆盖的「要决策」表达终归有限。交接 §7.4 已记录：本机 / 局域网的小模型语义检索**当前有故障**，`viking_search` 查已存在的记忆也返回空，embedding 服务（`192.168.3.111:8080`）历史上宕过。**所以在没有可用小模型通道前，B / C 里的「调模型精判」不可落地**，硬做只会让脚本每次都失败。

### 我的推荐

**先走 A（正则/关键词粗筛），并把止点定清楚**：
- 覆盖你常见场景（方案类、审批类、问「怎么办/怎么弄/行不行」）；
- 用**一组明确的触发词 + 一条可增补的「同义说法」清单**，方便你边用边加；
- 明确写死「不能每轮都注入，命中才注入」的判定，用会话日志实测「不误伤」。

**B/C 作为后续升级**：当模型通道恢复后（embedding / 本地 LLM 可用），把 A 当粗筛、模型当精判。现在不硬上，避免每次都坏。

请确认：**先 A 再升级（推荐）** / 直接用 B或C（需你确认模型通道可用）/ D（每轮固定注入）。

## 4. 待拍板项 4：注入的提醒内容是什么

### 背景

注入的是**提醒**，不是替你写文档。要短（每轮命中时都占上下文）。

### 我的方案（沿用单一真相源原则：只给指针，不抄正文）

注入这样一段（约 150 字）：

> 【汇报规范提醒】本轮用户疑似在请你做决策 / 审批。若确需用户拍板，请按「汇报语言与审批材料规范」四条硬规则执行（正本：`viking://user/memories/preferences/huzilin/汇报语言与审批材料规范.md` → 摘要见 `~/.dsh/AGENTS.md`「汇报与审批材料规范」段）：①中文展开说 ②不许甩词条/行号 ③要审批先落盘审批文档（含原文照抄+语境+选项与影响）④性质分类标注。若本轮只需技术澄清、无需用户拍板，忽略本提醒即可。

要点：
- 引用规范**正本 URI**（`viking://...`）与**摘要指针**（`~/.dsh/AGENTS.md`），不复制正文，守单一真相源；
- 自带「若无需拍板则忽略」的降级说明，避免把「提醒」变「强制」。

请确认：**就按这个内容（推荐）/** 想改措辞 / 想在注入内容里直接嵌入规范摘要正文（不推荐——违反单一真相源）。

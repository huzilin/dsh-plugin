**（4）为什么这件事现在必须补**：`status` 是 plan 闭环的**关键字段**——

- 插件靠 `status` 判断一张票是「未完成 / 进行中 / 已完成」（`displayStatus()` 读 `status`，词表：`done`/`closed`/`open`/`doing`…）；

- 缺陷要能进 tab、要能显示「待修 / 修复中 / 已关闭」，**必须有可读的 `status`**。

### 6B. 状态词表怎么定——**已裁定：可**【实测】

**缺陷有两种状态，别混**（实测两份真实台账）：

| 层级 | 是什么 | 现状 | 谁在用 |
|---|---|---|---|
| **文档级** `status` | 整个台账文件的生命周期 | `open` / `active`（两种写法都有） | plan 插件（判分类） |
| **条目级**「状态」列 | 每条缺陷的返工状态 | 新建 / 已确认 / 修复中 / 待复测 / 已关闭 / 挂起 | **骨架已规定**（C 节 + 总览表） |

**条目级词表骨架里已经有了**，原文：

> **C. 返工与复验记录**：状态（**新建 / 已确认 / 修复中 / 待复测 / 已关闭 / 挂起**）/ 原因分类（程序错误 / 需求变更 / 需求缺失 / 设计缺陷 / 环境 / 数据）/ …

**但实测真实台账没照它写**：dsh-flow 用的是「已修复（复测 PASS）」「已拍板关闭（最小原则，非缺陷）」这类**自由文本**；novel 用「已关闭」「新建」。

**裁定（本轮「可」）**：

- **文档级 `status`**：用 `plan-protocol` 既有五态（`pending`/`closed`/`active`/`abandoned`/`superseded-by`）——**不新造词表**，与 plan 生态对齐。缺陷台账全关闭写 `closed`，还有未关闭写 `active`。
- **条目级「状态」**：骨架既有六词**照用，允许附注**（如「已修复（复测 PASS）」）——插件解析时**取首词**匹配即可（`statusWord()` 已是此逻辑：按 `[\s(#:—-]` 切首词）。
- **不为缺陷另造条目状态词表**——骨架六词够用，再造即双真相源。

### 6C. 怎么保证和 plan 闭环——**已裁定：plan-lint 先不管**【实测 + 推断】

「闭环」= 三件事接得上：**文档能读 → 状态能判 → 门禁能查**。现状前两条是断的。

| # | 环节 | 现状 | 要做什么 |
|---|---|---|---|
| 1 | **文档能读** | ❌ 缺陷台账头部写在围栏/引用块里，插件读不到 | 骨架给**缺陷台账**补 frontmatter 规定；产物改成真 frontmatter（`---` 包裹） |
| 2 | **状态能判** | ❌ 缺陷被当工单；cases/test 也混进工单页 | 插件加 defect 分支 + **qa 组只保留 `type: qa-defect`**（6.3 第 2/2b 项） |
| 3 | **门禁能查** | ⚠️ `plan-lint` 整目录跳过 `qa` | **裁定：先不管**（保持现状） |

**「先不管」的含义**：`plan-lint` 的跳过集合 `['.archive','node_modules','assets','qa']` **保持不变**，qa 目录仍不纳入结构校验。校验职责留在 skill 侧自检（那 10 条 blocker/major）。代价是：**缺陷台账的头写错了，lint 不会报**——由 skill 自检与人工复核兜。

### 6D. 顺带：plan-protocol 的 type 词表也要扩【实测】

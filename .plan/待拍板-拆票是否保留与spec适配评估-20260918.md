# 待拍板：拆票这一步要不要留——「只适配 spec」能不能替代 to-tickets

> **你的原话（照抄）**：
> 「那你的方案是什么，我现在倾向于，**不走 to-ticket**，现在基于什么拆票，**spec 么**？**如果是 spec，那我们只要适配 spec 是不是就可以了**？」

> **一句话回答**：**拆票确实是基于 spec，但"适配 spec"替代不了它——因为 spec 和票不是同一层东西**：spec 说"要什么"（1 份），票说"分几步做、谁卡谁"（N 份）。**只读 spec，视图里就只剩 1 条，等于退回"看不见进度"。**

---

## 一、先回答"基于什么拆票"——是 spec（实测）

| effort | 拆票依据 |
|:--|:--|
| `ideation-fe` | 每张票的 frontmatter 都写着 `Source spec: .plan/ideation-fe/spec.md` |
| `wbflow-impl` | 票本顶部：「把 `.plan/wbflow-impl/spec.md` 拆成 17 张 tracer-bullet 工单」 |

**所以链路是**：`to-spec` 出 spec → `to-tickets` 把 spec 拆成 N 张票。**你问的前提成立。**

## 二、但"适配 spec"替代不了拆票——三条实测依据

### 【实测】性质 1：**粒度差一个量级**

| | spec | 票 |
|:--|:--|:--|
| `ideation-fe` | **1 份** | **7 张** |
| `wbflow-impl` | **1 份** | **17 张** |

**只读 spec → 视图里 1 个 effort 只有 1 条。** 那正是你之前抱怨的「看不见」的状态。

### 【实测】性质 2：**spec 里没有可执行单元**

`ideation-fe/spec.md` 的结构是：

```
Problem Statement / Solution / User Stories /
Implementation Decisions / Testing Decisions / Out of Scope / Further Notes
```

**验收项 checkbox 数 = 0，阻塞边 = 0。**

而票的核心特征是：

```
**What to build:** …
**Blocked by:** …
- [ ] 验收项（每票 1~6 条）
```

**`ideation-fe` 能"票 1 先行、票 2/4/6 并行"，全靠票上的阻塞图**——spec 里根本没有这个东西。

### 【文档已写明+实测】性质 3：**生命周期不同**

- 票有 `status`，且**被逐票回写**（实测：`ideation-fe` → 01/02/03/04/06 `done`、05/07 `open`）
- spec 的 `status` 是 `active`/`closed`（**文档级**），**不表达"做到哪一步"**

## 三、你方向里的**合理内核**（我采纳）

你的直觉不是全错——**你真正想消除的是「多一个 skill、多一层转换、而且转换还会格式出错」的成本**。

这个诉求成立，而且本轮已经回应了一部分：

> **`to-tickets` 的落盘规则已修**（一票一文件 + 补 map.md，commit `ced3741`）→ **格式错不再复发**。

**所以"不走 to-tickets"实际能省的，只有"拆票"这一步**——而这一步恰恰是**不可省的方法论产出**：

> `to-tickets` 第 3 步的 vertical-slice 规则（18 行）：每票须**切穿各层的窄纵切**、**完成即独立可验证**、**适配单个 fresh context**，并对 wide refactor 给 expand–contract 例外。

**这套切法是别处没有的。**

## 四、我的方案（三选一）

| 选项 | 做法 | 好处 | 代价 |
|:--|:--|:--|:--|
| **A（推荐）** | **维持两段式**：`to-spec` 出 spec → `to-tickets` 拆票（**格式已修对**）；**补上唯一的缺口**——加一个**收口 skill**（`plan-sync`）：读 `.plan` 的票 → 对照 git 提交判定完成 → **回写 status** | 三段齐备：**定需求 / 拆票 / 维护状态**；不动上游 | 多一个 skill |

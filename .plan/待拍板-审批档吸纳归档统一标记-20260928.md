# 待拍板：审批档吸纳归档的统一标记机制（对齐稿，未实施）

> **状态**：对齐阶段材料。用户已明确「还没让你实施，现在还是对齐阶段」——本文档只做对齐，**设计落盘（总表改写）/ 立票 / 旧裁决回扫**均未执行，待拍板后按拍板落地协议办理。

## 背景与用户原话（照抄）

现行口径（2026-09-28 早间落总表 §三·补「额外（已拍）」条款 + OpenViking 事件「审批档吸纳后归档定案」）：拍板结束（closed）后结论被 spec 或全局文档吸纳，**吸纳完成时审批档翻 `status: superseded-by:<归宿路径>`**——嵌入状态机。

用户在审阅该条款时提出（原话）：

> 审批档吸纳后标记归档 谁来翻，to-spec 可以基于拍板文档么？如果支持是不是应该是 to-spec 来做这个事情，并且标记要和其他保持一致，直接单独标记归档即可，不用嵌入状态机。
>
> 所有文件的归档标记保持一致。

即三件事：①吸纳翻标的责任人；②to-spec 能否以拍板文档为输入；③归档标记脱离状态机、全体系统一。

## 实测事实（性质：文档已写明 / 实测）

1. **to-spec 现行输入面不含拍板文档**【实测，两版正本】。本仓正本（`packages/dsh-plan-view/skills/to-spec/SKILL.md`）与 mp 原版（`workdir/skills/skills/engineering/to-spec/SKILL.md`）输入均为「当前会话上下文 + 代码理解 + CONTEXT.md/ADR」（本地版另加架构正本）；全文无「审批档/拍板文档」字样。→ **「to-spec 基于拍板文档」现状不支持，需加条款**。
2. **拍板的持久载体就是审批档**【文档已写明，grilling 原文】：「Record each ruling as it lands — quote their words verbatim… The document is the record; a ruling that lives only in the chat is lost when the session ends.」跨会话场景下 to-spec 只有显式读审批档才能拿到拍板。
3. **to-spec 已有天然挂点**【文档已写明，本地版】：「discharge the spec into its long-lived homes」要求 **spec 定稿时刻**逐节写归宿行（「at the moment the spec is finalized, not later」）。翻标若挂同一时刻，零新增时机、零新流程。
4. **mp 原版的 `superseded-by` 语义本来就是「被后续拍板取代」**【文档已写明，grilling 原文】：「set its status to `closed` (or `superseded-by:<path>` if a later decision replaced it)」。现行口径把「吸纳」也塞进该状态属**语义超载**；用户提议实际是回归原版语义。
5. **归档标记已有先例（总表 R1，已拍）**：归档成员头部 `archived: <round-id>`（无 frontmatter 的文件在首行加 `<!-- archived: <round-id> -->` 注释），写入动作在归档九步之③。

## 评估（性质：我的推断）

- 「to-spec 来翻」**成立且结构最优（限 spec 吸纳路径）**：它已是唯一在「吸纳时刻」必然在場的 skill，翻标与归宿行同一动作完成；前提是给 to-spec 加两条条款——①输入面显式纳入 `.plan/` 审批档（跨会话可追溯）；②吸收完成的审批档打归档标记。

- 统一标记若成立，票 09 grill 议题 **G1（审批档归档处置三选）获得机械判别器**，三选可收敛 → Q3。
- **连带影响（拍板后需回扫，本轮未动）**：总表 §三·补额外条款改写；OpenViking 事件「审批档吸纳后归档定案」加改判标注；plan-lint 可选校验对象从 superseded-by 改为归档标记。**票 07（spec 取代登记）不受影响**——spec 不是审批档，其 `superseded-by` 判据维持。

## 待拍板四项

### Q1 翻标责任人范围

- **是什么**：spec 路径翻标归 to-spec；非 spec 吸纳路径（词汇表/ADR/全局文档直接吸纳）谁翻。
- **从哪来**：用户原话「如果支持是不是应该是 to-spec 来做这个事情」只覆盖 spec 路径；拍板结论被全局文档直接吸纳的场景真实存在（如词汇表词条、ADR）。
- **影响什么**：plan-protocol 是否新增通则条款；漏翻时由谁兜底巡检。
- **选项与取舍**：
  - **A（推荐）**：**通则「谁吸纳谁翻标」写入 plan-protocol**，to-spec 为 spec 路径的具名实例。覆盖所有路径、不依赖某个 skill 恰好在場；通则一句话成本低。
  - B：全部归 to-spec。词汇表/ADR 吸纳不经过 to-spec，责任落空，漏翻无主。
  - C：全部归 plan-approve。它管审批档生命周期但不在吸纳时刻在場，只能事后巡检、无法当场翻标。

### Q2 标记的统一形状

- **是什么**：「所有文件的归档标记保持一致」统一到什么程度。
- **从哪来**：用户原话「标记要和其他保持一致，直接单独标记归档即可，不用嵌入状态机」；既有 R1 形状 `archived: <round-id>`。
- **影响什么**：所有文件的头部字段形状、读前拦截的 grep 模式、plan-lint 校验规则。
- **选项与取舍**：
  - **A（推荐）**：**字段名统一 `archived:`，值按场景**——轮归档成员 = round-id（R1 已拍形状不变），被吸纳审批档 = 归宿路径；读前拦截统一 `grep '^archived:'`，一类标记全体系可查。改动最小，不推翻已拍形状。
  - B：值也统一为路径（轮归档也写全路径）。字面最一致，但推翻 R1、写冗长路径，收益仅是值格式统一。

### Q3 已吸纳审批档在轮归档时的物理处置

- **是什么**：打了 `archived:` 标记的审批档，plan-archive 整轮搬移时跟不跟着走（现行 G1 三选的焦点）。
- **从哪来**：票 09 裁定「审批档留 `.plan/`」与 plan-archive「待拍板散件当轮成员搬走」存在冲突，原拟 grill 三选。
- **影响什么**：G1 是否还需要 grill；`.plan/` 是否无限堆积；轮快照是否完整。
- **选项与取舍**：
  - **A（推荐）**：**已标 `archived:` 者随轮搬**（内容权威已在归宿文档，搬走 = 出检索面、无信息损失）；**未标者留 `.plan/`** 不动。G1 三选收敛为「看标记」的机械判别，grill 议题可撤。
  - B：已吸纳的也永留 `.plan/`。轮快照少一块，但 `.plan/` 持续增长。
  - C：维持 G1 三选 grill 不收敛。多一轮流程，但保守。

### Q4 ADR 是否纳入统一 `archived:` 归档标记

**【已拍 2026-09-28】判 A，且比 A 更进一步**——用户原话照抄：「那我们就敲定，这个不由 plan-protocol 来管理。这个我们依然不主动归档。」两点：①ADR 不纳入 `archived:`、不主动归档（= A 案）；②**ADR 治理条款不入 plan-protocol**——落 domain-modeling 系（mp 原版家族 skill + ADR-FORMAT），plan-protocol「文件类型与获取」不覆盖 ADR。已同步总表三·补3 归属句与断链清单第 1 项口径。**Q1–Q3 仍待拍。**

- **是什么**：「所有文件的归档标记保持一致」是否延伸到 ADR——ADR 被推翻时也打 `archived:` 标记，还是维持自身 status 状态机。
- **从哪来**：用户问「adr 和待拍板能对齐么？还是每一次都能对齐，参考 novel」（2026-09-28）。ADR 已有已拍机制（总表三·补3：frontmatter 必填化 + 废弃**原地标废** `status: superseded by ADR-NNNN` + 读前拦截）；mp 原版 ADR-FORMAT 的 superseded 枚举 2026-04-17 即有。
- **novel 实证（2026-09-28 实测）**：novel 有 **4 份 ADR vs 40+ 份待拍板**；**双向零互指**——待拍板文档无一引用 ADR（grep 零命中），ADR 也无一指向 `.plan/`。对齐不靠链接：ADR 正文自述来源（ADR-0004：「状态：已接受（2026-09-25 用户拍板，架构评审候选 4 处置）」+ 用户原话留痕），来源件易逝时（HTML 评审报告）把证据摘要**内联**进 ADR。且 ADR-0004 的来源根本不是待拍板而是架构评审裁定——拍板载体多样，ADR 只认「过了三门槛的裁定」。
- **影响什么**：读前拦截检查哪个字段（ADR 查 `status` 还是查 `archived:`）；ADR-FORMAT 条款是否要改；「统一标记」的适用边界。
- **选项与取舍**：
  - **A（推荐）**：**ADR 不纳入 `archived:`，维持自身状态机**。划线依据：**过程层 vs 知识层**——待拍板是过程记录，死了 = 内容已转正进权威文档，归 `archived:`；ADR 本身就是权威知识，被取代是「知识更新」不是「归档」，superseded ADR 仍留原地供考古（原版语义 + 三·补3 已拍原地标废不搬）。词汇表词条同理（三·补2 三态已拍）。`archived:` 限定过程层（tracker 区轮成员 + 被吸纳审批档），一类标记覆盖所有过程死件，`grep '^archived:'` 一查全出；知识层各自类型内已自洽。两层的**对齐接缝**只有两个动作：①**晋升**——拍板过三门槛（难逆转/无上下文会惊讶/真实取舍）时当场立 ADR、正文记来源；若来源是待拍板档，该档按 Q1 通则由「吸纳者」（此处 = 立 ADR 的动作）翻 `archived:`。②**推翻**——新拍板推翻旧 ADR，旧 ADR status 翻 superseded（读前拦截已拍），新裁定的载体照常走过程层生命周期。**不是每次拍板都晋升**：三门槛稀疏准入（novel 4:40+ 即实证）。
  - B：ADR 也用 `archived:`。字面全统一，但推翻已拍的 ADR 原地标废机制、偏离原版 ADR-FORMAT，且「归档」语义不对——superseded ADR 是仍有效的知识记录（禁止照废弃案开工≠文件死了），不是搬出检索面的死件。

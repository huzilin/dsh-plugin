## 一、结论先行（四句）

1. **冲突的形态是「同一片领域上多份文档同时自称有效」**，而 mp 的原方案**靠「留存 + 只关不删」**处理历史结论——**它不提供任何「谁取代谁」的机制**。【实测】
2. **我方为补这个缺口自建了 `plan-archive`（归档）**，思路是「把过期文档搬走」。**但搬走只在归档时发生**——**归档之前那段窗口期完全无防护**，事故正发生在窗口期内。【我的推断】
3. **我方历轮整治的动作是「给旧文档补废弃标记」**（方向对），但实测发现**标记写在了 agent 读不到的位置**（30 份标记中仅 7 处可机械检索；最差的两份埋在全文 84%/88% 处，而 agent 先读头部）。【实测】
4. **不是「agent 写不出好的废弃声明」**——novel 现存最好的一份（`v1.0-design.md` 头部 17 行四部分声明）**就是 AI 写的**。难的是**时机**：错过「新权威落盘那一刻」，成本从「顺手」变成「一次专项考古」。【实测】

## 二、冲突是怎么发生的（完整机制链，本会话前几轮已逐段查明）

### 2.1 触发条件：一次大需求 = 一张 effort，但同一个域会被反复触碰

【实测】novel 现状：**17 张 effort 并存**，其中 `outline` 域被 **11 张图**改过。图的切法是**按变更单元**（一次大需求／一类问题／一批债务），**不是按领域**——所以**同一片代码/设计会被多张图先后改**。

**这是冲突的土壤**：每张图都会产出自己的 spec / 文档，而这些文档**都描述同一片领域**。

### 2.2 mp 原方案的处理：留存一切，不做取代登记

【文档已写明】上游 wayfinder（mattpocock/skills `engineering/wayfinder/SKILL.md:99`）的 `Out of scope` 机制原文：

> Out-of-scope work never graduates (the frontier stops at the destination), so it returns only if the destination is redrawn, and then as a fresh effort, not a resumption.

**注意**：上游只规定了「越界工作怎么回来」（以新 effort 回来），**没有规定「回来的新 effort 与旧图是什么关系」**、**更没有规定「新结论如何登记它取代了旧结论的哪些部分」**。

【实测】上游 `to-spec` / `to-tickets` 中 `supersede|deprecat|obsolet|stale` 命中数 **均为 0**（2026-09-28 对 `mattpocock/skills` `engineering/` 重测；仅有的 outdated 字样是「别把文件路径写进 spec，会过时」）。

**所以 mp 的原方案下，历史 effort 与票全部留存、且新旧之间无取代登记**——这是设计取向（issue 只关不删、一切留存），不是疏漏。它的隐含假设是：**图很少、串行推进、图与图之间不重叠**。【我的推断】

### 2.3 我方现状流程如何把「无登记」放大成「冲突」

本会话前几轮逐段查明，链路如下：

```
第 1 步：一次大需求开一张 effort，落一套文档（map + spec + tickets）
        ↓
第 2 步：图达成 destination → 翻 closed（或由 plan-archive 归档）
        但「关」只表示「不再推进」，不等于「其中的结论已失效」
        ↓
第 3 步：第二个需求（同域）开新 effort，产出新 spec
        ↓
第 4 步：新 spec 覆盖/推翻了旧 spec 的部分结论
        ——但 mp 原方案没有「登记取代关系」的动作
        ——to-spec 也不要求读旧 spec（实测 0 覆盖）
        ↓
第 5 步：新旧两份 spec 同时留在仓里，都自称有效
        ↓
第 6 步：【关键】后来任何会话（agent）读到旧 spec
        ——读不到「已被取代」的信号（标记埋在文末 / 压根没标 / 或头部仍写着「可交付实现直接照做」）
        ↓
第 7 步：照旧 spec 实现 → 废弃方案复活 → 冲突
```

**第 6 步是事故点，也是我方历轮整治试图堵的地方。**

### 2.4 具体冲突实例（已实测的三类）

| 类型 | 实例 | 冲突形态 |
|:--|:--|:--|
| **链式派生的多份「定稿」** | `docs/v1.0-design.md`（09-07 推演收敛）→ `.plan/ai-novel-workbench/spec.md`（09-07）→ `tech-spec.md`（09-07）→ `.plan/state-machine/双状态机设计定稿.md`（09-11） | **四代权威叠着活**；审计报告原文：「有三份文档都自称『定稿』，且互相矛盾」 |
| **节级取代（主症）** | `v1.0-design.md` 的 §6 审校域被双状态机定稿取代，但 §5/§7/§8/§9-§12 仍有效 | **部分取代**——协议只有「整份 `superseded-by`」，无节级登记 |
| **实现工单验收已打勾但验收旧口径** | 【文档已写明】审计原文：「**最危险的是实现工单**——它们的验收清单**已全部打勾**，但它们验收的是**旧口径**」 | 21 处冲突集中在实现工单 |

【实测】审计报告的量化结论：**66 处冲突（30 高 / 26 中 / 6 低）**，另有 13 份文档「整份或部分过时」；85% 的冲突集中在四件事（AI 审校产出物、批注状态集、修复触发点等）——**不是零散问题，是主干口径漂移**。

### 2.5 为什么「冲突」在当时无法被察觉

【文档已写明】审计报告发现一的根因原文：

> `docs/README.md` 把 `v1.0-design.md` 标为"可交付实现直接照做"——**实现者最先读索引，会优先照做旧口径**。而新定稿在老文档里**没有任何指针**。

**即：冲突不是「文档内容矛盾」（那反而好查），而是「索引指向旧权威、新权威无人指向」——一个照索引走的 agent 会照着旧口径实现，且全程不会遇到任何提示。**

## 三、我方自建的治理尝试，以及它为什么没解决

### 3.1 我方建了什么（两张表对照）

| 我方机制 | 治什么 | 为什么不够 |
|:--|:--|:--|
| **`plan-archive`（归档）** | 把走完的整轮搬进 `.archive/`，让旧文档不再污染新决策 | 【文档已写明】它自己的定位原文：「Plan 内容完成后会堆积……它们不删，但留在 `.plan/` 会**污染新决策**——下一轮 agent 读到一份过期 spec，会把其中已废弃的结论当真。**这就是 `.archive/` 存在的理由**」。**但归档只在轮走完时发生**，且**是整轮搬走**——活跃期无防护 |
| **「补废弃标记」**（历轮手工整治） | 在旧文档里标出「已废弃」 | 【实测】30 份标记中仅 7 处可机械检索；标记位置 5%~88% 不等，**agent 读头部时看不到** |

### 3.2 `plan-archive` 的标记规则本身缺两条

【文档已写明】`plan-archive:67` 原文（全家最接近需求的一条）：

> 给过时段落加标记：**谁取代它、何时、还留着有什么用**（三个要素缺一不可）

**它有「三要素」，但缺两样**：
1. **没规定位置**——「给过时段落加标记」是**就地标**（在被取代那节旁边），正对应实测的「84% 埋底」；
2. **只管归档期**——`:65` 那条「就地加偏差声明」也只针对「仍被实现引用、**不能随轮归档**」的成员，是**归档时的例外处理**，不是常态要求。

【我的推断】所以你历轮补的废弃标记，是**在一个「设计上靠归档搬走、不靠标记」的体系里加的一层体系外补丁**——方向对，但**体系没给标记规定位置**，因此它一直是散的、无法被 agent 稳定读到。

```
to-spec 写新 spec（不读旧 spec、不声明取代谁）          ← mp 原方案
      ↓
wayfinder 的 effort 一律留存（tracker issue 只关不删）   ← mp 原方案
      ↓
我方 plan-archive 归档整轮（只在轮走完时）                ← 我方补丁
      ↓
implement 读 spec（不检查是否已废弃）★事故在这里发生     ← mp 原方案
      ↓
我方历轮补废弃标记（散落、位置不定、埋底）               ← 我方补丁
```

**结论**：**「废弃」这件事，上游 mp 从未处理；我方用「归档 + 补标记」两个补丁去堵，但归档有窗口期、标记有位置问题——两个补丁都没盖住事故点（`implement` 读文档那一刻）。**（注：链路首环在本仓 markdown 适配器形态下表现为「同名 spec.md 复用覆盖」，在 mp 原版 tracker 形态下表现为「发新 issue 但无取代登记」——两种形态都无取代处理。）

## 六、证据：难的不是能力，是时机

### 6.1 最难的那份声明，是 AI 写的

【实测】`docs/v1.0-design.md` 头部的「部分过时声明」全长 **17 行**，含四部分：

```
① 一句话结论：审校/批注/状态机/版本相关章节已被《双状态机设计定稿》取代 + 新正本路径
② 受影响清单（勿据以实现）：§1 审校环节 / §6 审校域 / 批注状态机 / §14 审阅域 / 定稿触发关系
③ 仍然有效清单：§5 量化准则、§7 剧情推演、§8 语料基线、§9-§12
④ 冲突全量清单指针：.archive/state-machine-history/文档冲突审计报告.md
```

**第 ③ 部分「仍然有效」清单才是真正的难点**——需通读旧文档 14 节 + 新定稿 649 行，**逐节比对**，判定 5 节被取代、6 节仍有效。**这是领域判断，不是行文级别的活儿。**

### 6.2 但它就是 AI 做的，而且做得很好

【实测】追溯来源 commit `7cdeb7e`（2026-09-11 22:00），提交信息明列：

> ⑥docs: api.proto(v1.1端点)+adr/+**v1.0-design偏差声明**+CONTEXT.md

**该 commit 同时完成**：DSH ACP 后端化、审校 W1/W2、大纲编辑域、LLM 层重构、前端五页、台账三份。**这是一次 AI 主打的批量落地会话。**

### 6.3 真正的困难是三个

## 九·补、术语残留实证：为什么「批量替换」治不了「继续产出」

> **本节回答你的质询（照抄）**：「那你认为批量替换可以解决我说的场景？毕竟仅维护一个术语变更并不够，因为**强制提交这个问题就出现了多次，已经处理了多轮，但仍然在后续的工作中再次产出了强制定稿这个词**。」
>
> **结论：你说对了，批量替换不能解决。** 以下是实测证据。

### 9.1 残留规模（非归档区）

【实测】

| 指标 | 数值 |
|:--|:--|
| 旧词「强制定稿」在**非归档区**（排除 `.archive/`、`node_modules`）的出现数 | **141 处** |
| 其中带合法留痕标记（「原/旧『强制定稿』」）的 | **34 处** |
| **裸的（无留痕标记）** | **约 107 处** |

### 9.2 决定性证据：它**今天还在被新写入**

【实测】按 git 提交时间排序，「强制定稿」**最近出现的文件**：

| 时间 | 文件 |
|:--|:--|
| **2026-09-27 23:45** | `docs/architecture.md` ← **本日** |
| **2026-09-27 20:49** | `docs/词汇表.md` ← **本日（术语变更 SOP 的正本自己）** |
| 2026-09-27 19:33 | `fe/src/api/types.ts`、`be/api/v1/api.pb.go` |
| 2026-09-27 05:07 | `be/httpapi/router.go` |

**最讽刺的一条**：`docs/词汇表.md` 是术语变更 SOP 的**正本**，它自己**今天还被写入了旧词**。

### 9.3 三个结构性原因（为什么替换注定失败）

**原因一：「留痕要求」与「清零要求」互相打架。**
SOP 第 3 步明说「原话留痕标『历史引文』……不改写」——于是**每处理一次就合法地留下一批旧词**。【实测】`be/handler/author.go:259` 的形态：

```go
// ForceSubmit POST /api/chapter/:id/force-submit：【强制提交】（R12 §五，原「强制定稿」更名；
```

**这处旧词是"合法"的**。但**下次 grep 时，34 处合法留痕会淹没 107 处真残留**——**字面完全相同，一条正则分不出来**。

**原因二：旧词是「活的」——它还在代码标识符里，且有生产调用点。**
【实测】`be/domain/comment_state.go:53`：

```go
CommentActionForceFinalClose = "force_final"  // 动作 12：批量关闭（用户；R5 旧「强制定稿」语义，R12 后无生产调用点，边表保留）
```

**`force_final` 常量还在、边表还在**。**任何读到这段代码的 agent 都会重新接触到「强制定稿」这个语义，然后再写进新文档。** 这不是「忘了改」，是**「旧名所指的东西还活着」**。

**原因三：SOP 是「会话级」纪律，没有跨会话约束。**
SOP 第 5、6 步原文分别是「**本会话**……当场 sweep 铁律」「会话结束前对**本会话全部拍板**的废弃词合集跑一次……终验」。

**它保证「这次改干净」，不保证「下次不写出来」。**

【实测】`state-machine/map.md:21` 记录了当年 D-4 那轮：**「残留实况=活性表述约 16 处」**（已区分「活性」与「历史引文」并清理）。**但今天仍有 107 处裸残留**——说明**清完之后又被写回来了**。

### 9.4 机制层结论：现行三条机制**全是「事后清理」**

| 机制 | 生效时点 | 缺什么 |
|:--|:--|:--|
| 术语变更 SOP | **改的那一刻**（本会话 sweep） | 不防后续会话再写 |
| 废弃标注 | **旧文档被标记时** | 不防新文档再写 |
| `plan-archive` 归档 | **轮走完的那一刻** | 不防活跃期再写 |

**三条全是事后清理，没有一条是事前拦截。** 这就是「处理了多轮仍在产出」的机制解释——**每轮都在清理，但清理动作本身不产生「下次不许写」的约束**。

### 9.5 因此「批量替换」被撤回

【我的推断】批量替换只能处理**存量**（且被 34 处留痕干扰），**无法处理增量**。要阻断「再产出」，只有**在写的那一刻就报错**才有效（如提交时校验废弃词清单）——而它有一个**前置问题**：**机器分不出「合法留痕」与「真残留」（字面相同），所以先得给「留痕」一个机器可识别的形态**。

**另注**：你随后提出的「**spec 关闭 effort 后整体作废、docs 成为唯一长期权威**」方案，是唯一能**从根上消除「多权威并存」**的提案——详见治理档「三·补」节。

## 十一、mp 原版方案机制全貌（2026-09-28 调研，后续方案分析的依据）

> 本节是对真原版（mattpocock/skills，本地 `/Users/huzilin/workdir/skills`）的集中调研结论，作为后续一切方案分析（协议改造 / 引入取舍 / 新治理机制）的对照基准。全部【实测】，引注为原版仓内路径。

### 11.1 原版的存储与身份模型

map / spec / 票三类对象全部是 **issue tracker 上的不可变对象**（见〇节）：身份 = 平台原子分配、永不复用的 issue id；内容只追加（答案 = resolution comment）；close 不删；effort = 一棵 map issue + 子 issue 的独立子树，新 effort 必是新子树（fresh effort，`SKILL.md:99`）；**明文预期并发**（`:128`「expect other sessions to be editing the tracker concurrently」）。**防覆盖不是条款，是存储性质。**

### 11.2 各环节输入/输出契约

| 环节 | 输入 | 输出 | 关键原文 |
|:--|:--|:--|:--|
| **grilling** | ①对话带来的 idea/方案；②事实子代理（filesystem/tools）；③沉淀层（`CONTEXT.md` 词汇 + 已有 ADR） | 审批文档（status 五态；条目落定 closed / `superseded-by:<path>`，**「Never leave a document at pending once its items are gone — that is a lie the next session will believe」**） | 全文**无 spec 字样**；「Finding _facts_ is your job… dispatch a sub-agent」 |
| **domain-modeling** | `CONTEXT.md` + **代码**（与用户口述互证，冲突时**代码赢**：「Your code cancels entire Orders, but you just said partial cancellation is possible. Which is right?」） | 词汇 inline 更新 + 稀疏 ADR（三门槛：难逆 / 惊讶 / 真取舍） | 「Do not treat `CONTEXT.md` as a spec」 |
| **to-spec** | 对话上下文 + 代码现状 + 词汇 + ADR | **向已配置的 tracker 发布**：真 tracker（GitHub/GitLab）= 一条 issue + `ready-for-agent` 标签；local-markdown 配置 = 写 `.scratch/<feature-slug>/spec.md`（原版一等配置，`issue-tracker-local.md:6`） | 「publish it to the project issue tracker」 |
| **to-tickets** | spec / 对话 | 每票一条 issue（原生阻塞）或 `.scratch/<slug>/issues/NN-*.md` | 「Do NOT close or modify any parent issue」 |
| **implement** | **用户递入的 spec 或票** | 代码 + commit（tdd + code-review） | 全文 15 行；「Implement the work described by **the user** in the spec or tickets」；无 ADR/时效意识 |
| **triage** | tracker 入口新 issue | 五状态机（needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix）；redundancy check 对**代码**；被拒请求写 `.out-of-scope/` | 「search for an existing implementation… by domain concept」 |

### 11.3 知识流：单向漏斗，spec 不回流

```
对话 → grill（读：代码 + 词汇 + ADR） → spec → tickets → 实现
                  ↑________ 只有「结晶物」回流：代码 / ADR / 词汇 ________↑
```

- **grill 不读旧 spec**：grilling 全文零 spec 引用；domain-modeling 只对照词汇与代码。
- 旧结论若仍有价值，必然已**结晶**进代码 / ADR / 词汇之一；没结晶的部分，原版**认定不值得回流**（ADR-FORMAT：「If a decision is easy to reverse, skip it: you'll just reverse it」）——**接受信息损失，换「回流的全是为真之物」**。
- **ADR 是唯一的决策回流通道**：读 ADR = 读「过去拍过的板」，不是读「过去那轮的推演全文」。

### 11.4 ADR 冲突：字段备了，手续没配

- **格式层**：`engineering/domain-modeling/ADR-FORMAT.md` status 枚举含 `deprecated | superseded by ADR-NNNN`（2026-04-17 随文件诞生即有），但属 **Optional**（「Most ADRs won't need them」）。
- **程序层**：**无任何环节负责写它**——domain-modeling 唯一扫 `docs/adr/` 是**为编号**（「Scan `docs/adr/` for the highest existing number」）；写新 ADR 无「找出被推翻旧档并标注」步骤；to-spec/to-tickets 只说「respect ADRs」且无平局规则；grill 对照的是词汇与代码，ADR 之间互不对照；无 lint 校验互斥。
- **worked example（纸面推演：新增 ADR-0002 部分推翻 ADR-0001）**：0001 原样躺平；词汇表被强制即时更新（**全协议唯一有硬性即时写要求的沉淀物**——「update `CONTEXT.md` right there. Don't batch」）；「说法 vs 代码」的矛盾会在 grilling 被目击，但 skill 义务到「surface it」为止，**不在文档登记**；下游若读到两份并存，tie-break 无协议（模型默认按新者，属推断非规则）。**终局：两份「都成立」的 ADR 并存，答案散在模型猜测、人的记忆、代码现实三处。**

### 11.5 半读与窗口期：原版的真实风险面

- **半读**：ADR 无索引、新档无义务回指旧档，「只撞见旧 ADR」结构性可能；「respect ADRs in the area」无「必须全读」的明文——偷懒单文件命中不违反任何规则。
- **窗口期互证**：新拍板已落、代码未改的窗口内，旧 ADR + 旧代码（+ 未变化的词汇）**一致指向旧世界**；「代码会揭发冲突」**迟到一个实现周期**才生效。
- 原版的三道缓解全是概率压制：**读全交给便宜性**（一份 ADR 一段话，全读更省力）、**读对交给代码对账（迟到）**、**不冲突交给门槛（三门槛压低翻烧饼频率）**——没有一条是保证。

### 11.6 原版期望的用法

- **不期望用户维护一份长期权威文档**。长期真相分散四处、全由 agent 在协议内顺手维护：**代码**（现状权威）+ **ADR**（决策与取代）+ **`CONTEXT.md`**（词汇）+ **wayfinder map**（每 effort 决策索引）+ **`.out-of-scope/`**（被拒请求库）。**用户只负责拍板与递料。**
- **spec 事实上一次性**：发布 → 拆票（票反指 Parent）→ 之后协议内无人再被要求读它。但**无明文作废条款**——是「自然死亡」（没人再读），不是「制度性作废」（宣布失效、禁止照做）。
- 防「废弃方案复活」的思路不是「维护一份正确的文档」，而是**釜底抽薪：让「agent 照某份文档做」这个动作在协议里不存在**（人路由 + 无索引 + 入口对账对代码）。

### 11.7 能力边界：三个成立前提（即触发条件清单）

| 前提 | 松动后果 |
|:--|:--|
| spec/票活不过自己那一轮 | 一旦被当长期权威反复引用，进入「无取代字段 + 无人收口」的裸奔区 |
| 取用靠人路由（无 agent 可自读的索引层） | 出现索引层后，「人递错」升级为「索引递错」，第一道防线失效 |
| 决策收口是纪律不是机械检查 | grilling 的 closed/superseded 规则靠执行，「忘收口」无兜底 |

三条同时成立时，「复活」基本无从发生；**任何一条松开，协议内无任何机制会拦**。上游 issue 簇（§七：#1114 / D217 / #1080 / #1099 / #1042）证明这些缺口已被多人独立撞上、至今无人综合。

### 11.8 后续方案分析的对照清单（本节的使用方式）

评估任何候选方案（协议改造 / 引入原版某机制 / 新治理工具）时，逐条问：

1. **身份**：工作对象的身份是否由「原子分配、永不复用」的机制保证（tracker / 发号器 / 等价物）？
2. **只追加**：历史结论是否只增不覆（追加式记录，还是可被重写的文件）？
3. **取代登记**：「新权威落盘那一刻」是否有**强制**工序登记取代关系（字段 + 责任环节 + 机械判据）？
4. **读取时检查**：消费端（implement / to-spec 的等价物）是否检查所读文档的新鲜度/有效性？
5. **易腐物落位**：易腐内容是否被挡在长期权威之外（一次性文档 / 归档），长期权威是否只存耐腐结论？
6. **路由方式**：agent 取用权威是否依赖可漂移的索引层，还是人路由 / 指针新鲜度有保障？

### 11.9 local-markdown 本地形态全景：合并目录树与生成时刻表

> local-markdown 是原版一等 tracker 配置（wayfinder 的显式默认兜底）。全部 mp 本地文件分两类：**tracker 类**（`.scratch/`，由配置决定）与**沉淀类**（仓内固定位置，与配置无关）。

```
<repo>/
├── CONTEXT.md                      【domain-modeling · 第一个术语落定当场懒创建 · 每次落定 inline 更新 · 长期】
├── CONTEXT-MAP.md                  【domain-modeling · 多 context 时才建 · 指向各分片 · 长期】
├── docs/adr/
│   └── NNNN-<slug>.md              【domain-modeling · 拍板满足三门槛（难逆/惊讶/真取舍）当场写 ·
│                                      编号=扫目录最大号+1 · 只增不改（取代靠 optional Status 行）· 长期】
├── .out-of-scope/
│   └── <topic>.md                  【triage · 维护者拒绝一个 enhancement 时 · 每拒一项一份 · 长期】
├── .plan/
│   └── <round>-<topic>.md          【grilling · 每轮提问先写盘再开问 · 状态头 pending→closed｜superseded-by · 一次性留档】
└── .scratch/                       ← local-markdown 配置下，「issue tracker」就是它
    └── <feature-slug>/             ← 一 feature/effort 一目录（两种原型可并存）
        ├── spec.md                 【to-spec · 对话收尾要 spec 时按七节模板整份写盘 · 无状态头 · 一次性】
        ├── map.md                  【wayfinder 开图会话 · 仅开过图才有 ·
        │                              五节初始态；增长=收口追加 Decisions-so-far 行/雾毕业删段/越界加 Out of scope 行 · effort 级留档】
        └── issues/
            └── NN-<slug>.md        【两族同住：wayfinder 决策票（Type/Status: claimed-resolved 行，
                                       开图建首批 + 每次收口 create-then-wire 新挂）与
                                       to-tickets 执行票（What to build/验收 checkbox/Status: ready-for-agent，
                                       拆票会话按依赖序一次写全）· 共同规则：一票一文件、
                                       Blocked by 行、编号最小者赢 frontier、评论追加在 ## Comments · 一次性】
```

**生成时刻表**：

| 会话动作 | 生成/写入的文件 |
|:--|:--|
| grilling 每轮开始前 | `.plan/` 审批文档（pending） |
| 术语落定 | `CONTEXT.md`（无则懒创建） |
| 拍板满足三门槛 | `docs/adr/NNNN-<slug>.md` |
| 维护者拒绝 enhancement | `.out-of-scope/<topic>.md` |
| 对话收尾要 spec | `.scratch/<slug>/spec.md` |
| wayfinder 开图 | `map.md` + 首批决策票 + 第二遍接 Blocked by |
| wayfinder 每收口一票 | 票内追加 `## Answer` + 回写 map 一行 + 雾毕业新挂票 |
| to-tickets 拆票 | `issues/NN-*.md` 执行票一次写全 |
| triage 会话 | 翻票 `Status:` 行 + `## Comments` 追加（AI 免责声明开头）+ 拒绝时新建 `.out-of-scope/` |

**三条原文未规定的缝**：①两族票共用 `issues/` 编号空间（都从 01 起），同 slug 混居时如何避让未规定；②wayfinder 关图后 to-spec 的 slug 沿用还是另起未规定；③本地形态无「有 map.md 才算 effort」的识别规则（该判据为我方 plan view 侧），map.md 只是 wayfinder 恰好留下的文件。另：`to-approval` 本体原版不存在（grilling 仅引用其格式）；research 产物无固定落点；`spec.md` 无状态头——本地形态的 spec 同样「作废无字段」。

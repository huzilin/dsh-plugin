## 一、要你拍板的是什么

原项 3 的一句话：**把「S1 同票两处漂移」「06 号票即兴形态解析失败」这类事故变成机器可抓**——一个只读 lint：sweep `.plan/**/*.md`，校验 ① frontmatter 字段与状态词表合法 ② 同一票 id 出现在两个目录（双档）③ 有 `tickets/` 的 effort 缺 `map.md`。抓到报清单，不擅改。

## 二、现状【实测】

- `packages/dsh-plan-view/` 下**没有** plan-lint skill，也没有 scripts/ 校验脚本——原项 3 从未落地。
- **新发现悬空引用**：插件「📖 说明」页（`src/client/PlanView.tsx` GuideView「看到状态不对怎么办」节）写着：
  > 先跑 `plan-lint` 查结构性漂移（同票双档、缺 map.md、缺状态头）；再跑 `plan-sync` 对账票面与实际进度……
  但 **`plan-lint` 这个 skill 不存在**（skills/ 目录实测仅有 plan-protocol / plan-archive / plan-sync / plan-approve / to-approval 等）。用户照着说明页找 plan-lint 会扑空。
- 对照事故史：09-03 的 06 号票（即兴形态解析失败）、09-17 的 S1（同票双档漂移）——两次都是人肉发现的，证明「靠会话自觉复核」不够【文档已写明，OpenViking 事件在案】。

## 三、选项与影响

- **A（推荐）：建独立只读脚本 + 修说明页引用**
  - 做法：`packages/dsh-plan-view/scripts/plan-lint.mjs`（Node 只读，无依赖：walk `.plan/**` → 解 frontmatter → 查双档 / 缺 map.md / 非法 status 词表 / 缺状态头的 approval），输出违规清单；说明页文案从「跑 plan-lint」改为指向该脚本的实际调用方式（如 `node …/scripts/plan-lint.mjs <repo>`），或由 plan-sync 头部第一步代跑。
  - 好处：说明页从「悬空」变「可用」；plan-approve 结算前可先跑一遍，假活口现形；轻、无误伤（只读）。
  - 代价：一个脚本 + 少量文档改动；规则要与 plan-protocol 第三节保持同版本（单一真相源仍是协议 skill，脚本只是执行者）。
- **B：不建工具，只修文案**
  - 做法：说明页那句改为「按 plan-protocol 第三节「文档形态约定」人工核对；回写对账用 plan-sync」。
  - 好处：零新代码。
  - 代价：漂移继续靠人眼；已有两次事故证明不够——原项 3 的动机落空。

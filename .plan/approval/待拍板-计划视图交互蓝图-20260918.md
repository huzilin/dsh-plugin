## 四、待拍板项

### 项 A：定向派地基（~~第一版：要不要补~~ 已撤销）

- **v2 修订**：第一版判定"定向派缺失、需补 `runSkillOnSession`"——**已核实推翻**。harness 经 Typert 已暴露 `sessionController.prompt` / `commands.execute(agentId, line)` / `subagents.prompt`，客户端按 `agentId` 即可令某 session 跑 skill / 派活。**无需改 harness**，插件侧接这些远程 API 即可。本项从待拍板清单移除。
- 余留细节（仍待定，但不阻塞）：插件接 `commands.execute` 时，要不要封装一个 `runSkillOnSession(sessionId, skillName, input)` 语义层，避免 UI 直接拼命令字符串。建议封装，但属实现细节，不单列拍板。

### 项 B：session 绑定存在哪（R1）— **已决：B1**

- **决定**：加 frontmatter 字段，沿用 plan-protocol「frontmatter 是权威」，不另起文件。
  - 票：`session:`（绑定的推演/执行 session id）
  - 拍板文档：`origin_session:`（产生它的 session）
  - 后台任务：挂 `sessionId`（派发时写回）
- **理由**：与现有协议一致、插件只读即可；避免 `bindings.json` 双源漂移（我们刚根治过）。
- **实现要点**：插件读 frontmatter 的 `session:` / `origin_session:` / `sessionId` 渲染「跳转」按钮；写回由派发动作（`commands.execute` / `subagents.prompt` 的返回里拿 sessionId）落盘。

### 项 C：非阻塞任务的"看执行状况"怎么呈现（R4）— **已决：C1**

- **决定**：任务列表显示 `sessionId` + 状态（running/done/failed，来自 session/subagent 事件）+ 一键 `openSession`。
- **实现要点**：状态从 `subagents.prompt` 的 `SubagentPromptReceipt` / `sessionController` 的 follow frame 派生；UI 轮询或订阅更新（见下方「动作后刷新」）。

### 项 D：④ 总览页（你清单第 4 点）— **已决：D1**

- **决定**：总览 = 阶段指示 + 跨 effort 聚合的 frontier / 最长等待 blocker / 最久 pending 拍板 + 点击跳转。
- **阶段模型**（派生规则）：
  - `决策循环①中`：存在 `status: pending` 的待拍板文档，且本 effort 无 open ticket。
  - `落地链②中`：有 open/claimed ticket 且 frontier 在推进。
  - `卡待拍板`：有 `pending` 拍板且它是最久未决者（用已有 age 计算）。
  - `卡 blocked`：有 ticket 的 `blocked_by` 未满足（frontier 空但仍有 open ticket）。
- **「卡在哪」算法**：跨所有 effort + root 待拍板聚合 → 列出 最久 pending 拍板、最长等待 blocker（open ticket 其 blocker 最久未翻）、各 effort 进度%；每条可点 `openSession` / 跳对应文档。
- **动作入口**：总览项点击 = 跳到卡住的票/拍板并（可选）触发对应动作（推演/拍板），与 ①②③ 共用动作层。

### 项 E：session 被回收的兜底 — **已决：E1**

- **决定**：跳转前先 `sessionQuery` 校验 session 是否存活；死则提示「该 session 已不可用，是否新建/恢复」。
- **实现要点**：`openSession` 前查 `sessionQuery.get(sessionId)`（或 `listSessions` 匹配），缺失则弹确认「新建 session 并重新绑定 / 取消」。

### 项 A（已撤销，见第二节 v2）：定向派地基无需补。

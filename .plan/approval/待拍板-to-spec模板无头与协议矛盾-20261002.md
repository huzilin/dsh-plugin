## 二、这段在讨论什么（语境）

**`to-spec` 是什么**：它是落地链的第二环起点——把已经谈定的结论「合成」成一份 spec（实施规格文档）。它有个特点：**不能由 agent 主动调用**（技能里标了「禁止模型自发调用」），只能由你手动跑 `/to-spec`。所以它写出来的东西，形态**完全由那份模板决定**。

**spec 在生命周期里的位置**：协议把它定义为「**一次性实施文档**」——「写『这一批怎么做』，**随 effort 生命周期；effort 关闭后作废并归档**」。它跟 map、票是一组（都属「官方有的」东西，落 `.scratch/<feature-slug>/`）。

**这件事和这两天改动的关系**：

- **昨天到今天上午**，我们刚把「状态」这个载体从文件头搬到了正文行，并明确「frontmatter 保留 `type`/`date`/`origin` 三个字段」。
- 那次改动**统一了所有文档的读法**——协议表格里 spec、票、审批档、缺陷、台账五类，全都写了「frontmatter 怎样 ＋ 正文行怎样」。
- **但 `to-spec` 的模板没被同步。** 表格说 spec 要有头，模板产出的 spec 没有头。

**这跟前一个待拍板（门禁那个）是同一类病**：上一轮是「协议改了、门禁没改」，这一轮是「协议写了、产出模板没写」。**两次都是"说明书之间不一致"，而且两次都是靠人偶然发现，没有机制兜住。**

**为什么必须由你决定**：这牵涉到 `to-spec` 这个 skill 要不要改，而它有几个特殊约束——

1. 它是**不能由 agent 自动调用**的环节，改了要靠你手动跑才生效；
2. 它的模板是从**上游 mp 原版**继承来的，改它要考虑「本仓自有改动 vs 原版一致」的归属问题（你在 09-27 专门立过这条纪律）。

## 四、待拍板项与选项

### 拍板项 A：spec 到底该不该有头？（定性问题）

这是**先决问题**——不定性，下面的动作都是瞎猜。

**选项 A1：spec 应当有头，改模板让它产出头（我倾向这个）**

- **理由**：协议表格已经明文要求了（【文档已写明】第 1 条），且 spec 是**会被门禁检查[5] 读 `superseded-by:` 的**——检查[5] 现在读正文首部 10 行。无头的话，`superseded-by:` 只能靠正文行，位置感会变弱。
- **代价**：要改 `to-spec` 的模板，并重新分发安装。
- **风险**：要确认改了模板不会破坏「与上游原版一致」的既有裁定。

**选项 A2：spec 就是无头的，改协议表格去迁就模板**

- **理由**：协议【文档有空白】第 1 条承认无头文件存在，且 `to-spec` 是上游原版行为。
- **代价**：要改协议表格里 spec 那一行；同时要回答「那 `superseded-by:` 写哪」（只能写正文）。
- **风险**：**这会开一个口子**——五类文档里唯独 spec 无头，读法就不再统一，agent 每读一个 spec 都要先判断「这份有没有头」。

**选项 A3：维持现状，靠人手补**

- **代价**：**每个写 spec 的会话都要记得补头**，而这不是机制保证的。按今天两次事故的教训（门禁漏改、模板漏改），「靠记得」正是已经失效的东西。
- **结论**：我不推荐，但列出来供完整性。

### 拍板项 B：如果选 A1，模板要产出到什么程度？

- **B1 补三字段头 ＋ 标题 ＋ 状态行**（完整对齐协议表格）
  - 产出形如：`---` `type: spec` `date: <today>` `origin: <?>` `---`、空行、`# <标题>`、空行、`**Status:** active`、空行、然后才是 `## Problem Statement`。
  - **问题**：`origin` 和标题从哪来？模板里没有变量机制，得靠调用时的上下文推断。
- **B2 只补三字段头，不补标题和状态行**
  - 更保守，但**状态行是门禁检查[5] 要读的**，不补的话 spec 的「作废登记」还是无家可归。

### 拍板项 C：要不要把「产出模板必须与协议一致」写成硬规则？

**这是和昨天那个「协议改则门禁同批改」配套的另一半。** 昨天的规则堵住了「门禁」，但没堵住「产出模板」——今天就撞上了。

- **提议**：在协议里补一条——**凡协议规定了某类文档的形态，产出该类文档的 skill 模板必须与之对齐；形态类拍板落地时，产出方（模板）与校验方（门禁）同批更新。**
- **需你确认**：是否采纳，以及挂在哪个 skill 下。

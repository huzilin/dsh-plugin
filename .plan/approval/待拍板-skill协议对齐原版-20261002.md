## 六·补二、`out_of_scope` 的票后续推进与结束（用户追问）

### 用户原话

> out_of_scope 的 ticket 后续要推进么，一般怎么结束？

### 答案：**不推进，它是终点**；但"怎么结束"这一步，**原版有缺口，我方有定义**

### 一、它不推进（性质：文档已写明）

原版 `wayfinder/SKILL.md:99` 原文照抄：

> **Out-of-scope work never graduates** (the frontier stops at the destination), so it returns only if the destination is redrawn, and then as a fresh effort, not a resumption.

**语境**：这段在讲"雾"与"范围外"的区别。雾（fog）是"还看不清、但方向对"的工作，会随地图推进**逐渐毕业成票**；范围外是"看清了、但超出终点"的工作，**永远不毕业**。

**三个要点**：
1. **不回到路线**——它的存在终点就是"被排除"这个判定本身；
2. **不是"以后再做"**——要重做只能重画终点，且**算一个全新 effort**，不是"接着上次"；
3. **不进 "Decisions so far"**——那里记"实际走过的路"，而范围外是路的边界，**不是路上的一步**。

### 二、"怎么结束"——原版写了一个动作名，但**没定义它**（性质：文档有空白）

原版 `wayfinder/SKILL.md:101` 原文照抄：

> Ruling something out of scope is a scoping act, not a step on the route. When a ticket that already exists turns out to sit past the destination (mis-scoped in while charting, or exposed by a resolution), **close it** (a closed ticket is unambiguously off the frontier) and leave one line in the **Out of scope** section: the gist plus why it's out of scope, linking the closed ticket. It stays out of **Decisions so far**, which records the route actually walked; a scope boundary isn't a step on it.

**它说了"close it"，但**——我核了原版那份 tracker 说明书（`issue-tracker-local.md`），**它只定义了两种结局**：

| 原版定义的动作 | 原文 | 写到什么状态 |
|:--|:--|:--|
| Resolve | `:30` append the answer under an `## Answer` heading, set `Status: resolved` | `resolved` |
| **Close（范围外）** | **—— 无定义 ——** | **未写** |

`issue-tracker-local.md:26` 的状态词表只有两个值：**`claimed` / `resolved`**。**没有第三个值给"范围外"用。**

**所以原版这里是个缺口**：wayfinder 说"close it"，但 tracker 说明书没定义 close 写成什么。**范围外的票在原版协议里没有合法的落笔形状。**

**这个缺口有历史代价**：本仓 2026-09-03 出过一次真实事故——某张票的作者**自己发明了一个形状**（frontmatter 写 `out_of_scope: true` + 标题写 `## Status：Ruled out`），因为协议没告诉他该写什么。结果**解析器不认，票显示在 "Open" 列**。

### 三、我方怎么补的（性质：我方自建，已有定义）

我方 `TRACKER-MARKDOWN.md` 定义了一个**独立的收束节**：

> A closing section — `## Answer`, or **`## Ruled out`** — is appended on closure, not written up front.

派生规则：

| 票面有 | 派生状态 |
|:--|:--|
| `## Answer` **带正文** | `done` |
| **`## Ruled out` 带正文** | **`out_of_scope`** |
| 两者都无，且有 `claimed_by` | `claimed` |
| 都没有 | `open` |

**关键设计：它是"派生"的，不是"写一个状态字段"。** 写收束节这个动作**本身就是结束动作**——没有第二次编辑可忘。这恰好补上了原版的缺口（原版那个"close"动作没有载体）。

**两条硬约束**（我方已有，且是防事故的）：
1. **只有"带正文"才算数**。光写个 `## Ruled out` 标题、下面空着，**不算结束**——票还在原地，仍是认领态。这是防"写标题就死掉"的会话；
2. **`## Answer` 与 `## Ruled out` 不能同时出现**。一张票要么是路线的一步，要么是它的边界，**不能两者都是**。

### 四、范围外票的完整生命周期（本仓现状汇总）

```
   票被判定"超出终点"
        ↓
   写 `## Ruled out` 节 + 正文（说明为什么范围外）
        ↓
   派生状态 = out_of_scope
        ↓
   ① 在地图 "Out of scope" 区留一行（要点 + 为什么 + 链接该票）
   ② 不进 "Decisions so far"
   ③ 退出 frontier，永不毕业
   ④ 不满足任何阻塞边（下游票永不解锁 —— 这是信号，不是 bug）
   ⑤ 进度统计中分子分母均剔除
   ⑥ 视图路线图从主网格移到侧栏单独展示
        ↓
   （终态。只有重画终点才会以"新 effort"形式回来）
```

### 五、那条"下游永不解锁"要专门说

我方协议明文（这也是最容易被当成 bug 的地方）：

> `done` 和 `out_of_scope` 不是两种"结束"。`done` 意味着路线走过这张票；`out_of_scope` 意味着这张票在终点之外、路线刻意不走。**只有 `done` 满足阻塞边**——被 out-of-scope 票阻塞的票永远不会解锁。

**关键理解**：如果一张票被范围外票阻塞着、因此永远做不了，**这不是要修的故障，而是信号**——说明"这张被阻塞的票"和"那张范围外的票"里，**有一张的范围划错了**。协议原话："one of the two is mis-scoped, and you should say which."

### 六、对你那句"等效 closed"的回应

现在可以回答得具体了：**`out_of_scope` 在"不再活跃、退出 frontier"这层上确实等效 `closed`**（原版原话 "a closed ticket is unambiguously off the frontier"）。**但在两个点上与 `done` 不等效**：

| 维度 | `done` | `out_of_scope` |
|:--|:--|:--|
| 退出 frontier | 是 | 是 |
| **满足阻塞边** | **是** | **否** |
| 计入"走过的路"（Decisions so far） | 是 | **否** |
| 计入进度分母 | 是 | **否** |

**所以读法一（语义等效结案）成立，读法二（阻塞边等效）不成立。** 若你要的是读法二，那是对现协议的反转，需你明说。

### 12.2 先答：`plan-sync` 是做什么的

**一句话：它是「票面状态 vs 实际做没做」的对账方**——落地链的**最后一步**。

流程位置（协议四步链条）：

```
to-spec 写需求 → to-tickets 拆票 → implement* 建出来 → plan-sync 对账
```

**它解决的具体问题**（skill 原文）：

> 一张票的 `status` 是**一个声明，没有任何东西强制它属实**。工作在一个从不回头翻字段的会话里做完了；另一些工作被标成完成、验收框却空着。于是票面告诉下一个会话**不真实的事**——要么"还没做"（其实做完了），要么"做完了"（却没有证据）。

**它怎么干**（4 个要点）：

| 步骤 | 做什么 |
|:--|:--|
| **判据** | **「按证据判，不看字段」**——`status` 是你正在检查的东西，所以它不能是你的输入。逐票问"要让它为真，得有什么存在"，然后去找 |
| **取证** | 最强证据优先：git 提交 → 代码存在 → 交叉引用（其他票/交接/台账记载它落地） |
| **写回** | 翻正文 `**Status:**` 行 → 勾验收框（**只勾有证据的**）→ 补一行落地注（commit 号 + 遗留） |
| **红线** | **「凭弱证据关掉的票，是这一趟绝不能做的事」**——指不出交付物就把票留开，并说明缺什么 |

**与 `implement*` 的分工**（协议硬规则 2）：**同一个动作的两种时机**——`implement*` 在每张票落地时**当场**翻；`plan-sync` **事后对账补齐**。不是两套流程。

**它后面还有什么**：`plan-sync` 是落地链终点。收尾后进 `plan-archive`（整轮归档）。

`plan-sync` 是落地链**最后一步**，而归档判据的证据**在它手上最全**（刚逐票核过）。所以让它**顺手核一遍 G4 四条**并**报告**（不执行）：

| 判据 | 它核什么 |
|:--|:--|
| ① 票全终态 | 全部 `resolved`/`out_of_scope`；有 `qa_cases` 的须有 `qa_accepted` |
| ② 缺陷全关闭 | 读**正文** `- 状态:`；**`待复测` 不算关闭**（与裁定甲联动） |
| ③ 图内台账全销 | **全局 `.plan/ledger/` 豁免**（不阻塞轮归档） |
| ④ spec 与审批档可搬 | spec 带 `superseded-by:` 或归宿行齐备；审批档全终态或已翻 `archived:` |

**红线写明**：「**不得为了清单好看去翻状态**——那会把这个 skill 的目的整个倒过来」。

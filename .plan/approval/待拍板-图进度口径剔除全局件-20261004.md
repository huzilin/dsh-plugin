# 待拍板 · 图进度条口径剔除全局件（effortProgress 的 own 集合收窄）

**Status:** closed

> **2026-10-04 全项裁定（用户原话「按这个来」）**：Q1 采 **A 案**（剔除全局件）；Q2 **确认 spec 名额维持不动**；Q3 采**函数内部收窄**。三项已落地，见文末「落地记录」。

## 一、这件事是什么

plan 视图上每张图（effort）都有一条进度条，读数由 `dsh-plan-view` 的 `effortProgress()` 函数算出。这个函数算分子分母时，取的不是「这张图自己的单据」，而是：

```
own = tickets.filter(t => t.effort === e.dir || t.effort === ROOT_GROUP)
```

也就是说，**`.plan/` 根层下的全部全局件（全局台账、全局缺陷、全局待拍板档）都被算进了每一张图的分母**。

用户指出：「master-outline-realign 本身的台账是 0，你是算了全局的么，这个是不应该的。待拍板也一样，不算 N 全就。」

实测复现（novel 仓 master-outline-realign 图，读数 44%）：可数单据 47 张 + spec 名额 1 = 分母 48，结案 21 张 = 分子 21，21 ÷ 48 = 43.75% → 44%。其中属于全局件的有：**全局台账 7 条（0 条结案）、全局缺陷 2 张（0 张关闭）、根层待拍板 6 张（全部 closed）**——这 15 张与 master-outline-realign 这张图无关。

去掉全局件后，本图真实读数 = **45%**（本图可数 32 张 + spec 名额 1 = 分母 33，结案 15 张 = 分子 15，15 ÷ 33 = 45.45%）——构成：工单结案 10/16、图内待拍板结案 3/3、图内缺陷结案 2/13、spec 未归档占 1 个名额未得分。

注意：剔除后读数**反而升高**（44% → 45%）——因为全局件里 7 条台账 + 2 张根层缺陷全是未结案，剔掉它们等于把一批「不是这张图的欠账」从分母里拿走。这也说明本缺陷是**双向失真**：不只把无关欠账算进来，也可能把已办结的全局档（根层 6 张待拍板全 closed）算成这张图的成绩。真正反映本图欠账的是「图内缺陷 2/13」——13 张里 11 张未关闭，这才是 master-outline-realign 自己压着的活。

## 二、原文照抄（用户本次指示）

> master-outline-realign 本身的台账是 0，你是算了全局的么，这个是不应该的。待拍板也一样，不算 N 全就。

语境：用户先问「44% 是怎么算出来的」，助手给出计算拆解并复现 21/48；用户随即指出拆解里混入了全局件，判定这不该算进去。

## 三、相关条款关系（这是关键——协议已明文规定，代码违反了自己认可的判据）

**① plan-protocol 正本「全局件」条·判据归属（文档已写明）：**

> **判据归属**：全局件目录（`approval/`、`qa/`、`ledger/`）**不参与 effort 判据**——它们是全局件锚点不是图。

**② plan-protocol 正本·全局件推进入口（文档已写明）：**

> **全局件推进入口**：全局件不属于任何图，**图收口时天然被跳过**，故**唯一认领方 = plan-loop 的全局件行动行**。
> **全局台账/qa 不进入**归档前置判据③的清账范围——全局挂账长期「在挂」不阻塞任何轮归档。

**③ 2026-09-25 拍板（文档已写明，且已被代码遵守于别处）：**

> 2026-09-25 拍板：全部地图态聚合各图图内台账，**全局台账不进地图页**。

**④ 视图代码自己在别处的正确实现（代码已写明）：**

- 缺陷子页：`defects.filter(t => t.effort !== ROOT_GROUP && …)`（已剔除全局）
- 台账子页：`ledgers.filter(t => t.effort !== ROOT_GROUP && …)`（已剔除全局）

**⑤ 视图代码在进度条这一处的相反实现（本次问题点）：**

- 总览卡片：`tickets.filter(t => t.effort === e.dir || t.effort === ROOT_GROUP)`
- 地图子页头部条：同上（同一行写法，两处硬编码）

**结论：这不是「口径未定」，而是同一个只读渲染方内部两套口径打架**——地图子页列表已经按协议剔除了全局件，同一屏的进度条却把全局件算了进去。列表显示「本图 0 条台账」，进度条却因全局 7 条挂账扣 15 个百分点。

## 四、历史成因（我的推断，非文档明文）

2026-10-03 拍板④（有记录）写明：「新增 EffortProgressBar 组件（effortProgress 单一真相源）……selProg 的 own 改全量单据（**含根层全局件**）与总览卡完全同数」。

当时的**目的是「消除双口径」**——让地图头部条和总览卡读数一致（此前 Kanban 自算 done/active，与总览卡不同数）。这个目的达成了，但顺带把全局件固定进了进度口径。我推断：当时聚焦「两处数字要一样」，未回头核 plan-protocol 的「全局件不参与 effort 判据」条，属口径变更未走 sweep。

**这是我的推断，不是文档明文**——文档只记了「改成含根层全局件」，没记当时是否讨论过协议那条。

## 五、影响面

- **波及范围**：novel 与 dsh-plugin 两仓的所有图进度读数（凡有全局挂账/全局缺陷未结案者，读数一律偏低）。nvwa 等同结构仓同理。
- **严重度**：读数失真，但不影响任何单据本身的真实状态——列表页、台账页、缺陷页的筛选都是对的。
- **反向风险**：若把全局件全剔，会导致「图内全做完但全局压着一堆挂账」在总览页无任何提示。但这本就不是图的责任（协议明文：全局件唯一认领方是 plan-loop 全局件行动行，与图无关）。

## 六、选项与影响

### Q1（核心）· 进度条的分子分母该不该剔除全局件？

**A 案（推荐）· 剔除全局件，与协议及列表页对齐**
- 进度条只算 `t.effort === e.dir` 的单据。图内 0 条台账 = 不扣分。
- 优点：与 plan-protocol「全局件不参与 effort 判据」一致，与同屏的台账/缺陷子页列表一致，读数反映「这张图的活干完没有」。
- 代价：总览页看不到全局积压对项目的影响；但全局件本有第一层「台账」「测例&缺陷」页承载。
- 连带：总览卡与地图头部条仍保持同数（两处一起改，单一真相源不破）。

**B 案 · 维持现状（含全局件）**
- 维持 2026-10-03 的既有实现。
- 缺点：与协议「判据归属」条明文冲突，与同屏列表页自相矛盾，用户已明确判定「不应该」。

**C 案 · 进度条剔除，但总览卡另加全局件提示行**
- 进度按 A 案算；总览页另起一行显示「全局件：N 条挂账 / M 张缺陷未结」（不计入百分比）。
- 优点：A 案的正确性 + 全局积压仍可见。
- 代价：多一处 UI 改动（本项可另立票，不阻塞 Q1）。

**助手推荐：A 案**（若你认可 C 案的提示行，可作为 A 案的后续增量另立票）。理由：视图是**只读渲染方**，协议是判据正本；视图自造口径与正本冲突时应改视图，而不是改协议——除非你要改的是协议本身。

### Q2· 若采 A 案，spec.md 占名额是否也要收敛？

现状：实施图的 `spec.md` 固定占 1 个名额（未标 `superseded-by:` ⇒ 分母 +1、分子 +0）。spec.md 是**图内文件**（`.scratch/<slug>/spec.md`），不是全局件，故 A 案不影响它。**助手的判断：无需改动**，此项仅作确认，避免 A 案执行时误伤。

### Q3· 落地方式

- 若采 A 案：改 `effortProgress` 的两处调用点（总览卡 + 地图头部条），并补测试钉住「全局件不进分母」。
- 是否需要在 `effortProgress` 函数内部收窄（函数自己过滤 `ROOT_GROUP`，调用方不必再传对集合）？助手倾向**在函数内部收窄**——避免第三个调用点又写错（本缺陷正是「调用点各自拼集合」导致的口径漂移）。

### 上游机制补充（2026-10-04 用户分析入档，novel 仓实测坐实）

起草漏圈之上还有一层更上游的机制缺陷：**spec 退役时点过早，使「权威文档合并」的责任从 spec 归宿骨架转移到收口票起草清单**。

- **时间线（实测）**：spec.md 于 10-03 05:55（`e730787e`）按「票 01~10 全终态」判据标 `superseded-by`；此后票 11（13:33）、票 15/16（14:18）、票 17~20（14:47）全部创建于 spec 退役之后，QA 两轮在当日夜——**effort 后半程十张票全部活在「spec 已死」窗口内**。
- **判据缺陷，非执行违例**：plan-protocol 校验[5]「effort 票已全终态 ⇒ spec 必带 superseded-by」（2026-09-28 拍板）在当时视角下被满足、执行合规；但「票尽」是随时可被续批打破的动态状态（本案例当日即被 DEF 转票／语义裁决／通路拆票打破三次）。spec 退役时归宿行自写「具体实施形状归票（**本批未拆票**）」——退役时已知会有后续票，仍按判据退役。
- **实证一（spec 无法写入）**：DEF-27 头部明写「通路更换**触碰 spec 既有两条红线**，须先立项裁定红线去留」——修复要裁定的对象就是 spec 里的红线，裁定结果却无处进 spec（已成「决策来源留存」件），只能落拍板档与票。
- **实证二（归宿文档脱管）**：拍板档「已核正本」行与 spec 归宿行**都点名 architecture.md §7.5**（前者列为已核正本三件套之一、后者为 Implementation Decisions 节归宿），项四 sweep 清单仍然漏圈它——spec 死后，连它指定的归宿文档都脱离了机制眼界。
- **implement-spec 退化形态（实测）**：守门动作（spec 已 superseded 则停、读现行权威、票面记「已核新正本」）有执行痕迹（票 11/12/16 与拍板档均有三件套记录）；真正退化的是 spec 的「任务图＋决策收纳」双职能——口径一致性只能靠票间 blocked_by 与收口票 sweep 兜，即本缺口的空间。

## 三、为什么三道防线都没拦（机制归属）

1. **起草侧**：拍板档的「影响域/适配范围」由 AI 起草，无「权威文档全集对照」要件——to-approval 的档要仄件里没有这一条，清单漏圈无机制发现。
2. **裁定侧**：用户的裁定对象是清单本身。未列出者天然不在裁定面内——这是结构性信息不对称，不是用户疏漏。
3. **门禁侧**：plan-lint 查档形状/指针不查内容时效；QA 的 D-4「文档-实现一致性」用例，其对拍范围同样派生自 sweep 范围（票 20 内的三正本）——**门禁的覆盖面继承了起草的盲区**，盲区无法自我检出。

与既有条款的关系：「拍板落地与销号协议」⑥「口径变更必须当场 sweep」与「术语变更双域Sweep协议」的逐条销号，管的都是**已识别变更项要扫干净**；本案例暴露的是**识别清单本身的完备性无正本要求**——上游没有「权威文档全集」这个对照基准被要求过一遍。

## 四、影响面

- 非个例：凡「拍板涉文档适配」的拍板（术语退役、口径取代、机制改造）都走同一条「起草材料圈范围→拆票→sweep」链，起草漏圈即全链漏扫。novel 仓 2026-10-03 前的收口票均无「全集对照」动作，无一条防线曾要求过。
- 复发成本：权威文档与实现相悖是静默的——发现只靠人或人提问，发现时过时面可能已跨多个批次。

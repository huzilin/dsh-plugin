## 一、新方案下的文档分层（定稿）

> **一句话**：**docs 是唯一长期权威，spec 是一次性实施文档。**

```
┌─ 长期权威层（docs，持续维护、永不退役）────────────────────┐
│  ① arch 总纲          全仓唯一，写「系统是什么」            │
│  ② 领域文档          每域一份，写「本域内怎么定义/怎么算」  │
│  ③ 需求文档          写「用户要什么」（新增类）            │
└────────────────────────────────────────────────────────┘
              ↑ 单向派生（spec 把成果并入 docs 后即作废）
┌─ 一次性层（spec，随 effort 生命周期）──────────────────────┐
│  ④ spec.md           写「这一批怎么做」；effort 关闭后作废 │
│                      归入 .archive/（过程留档）            │
└────────────────────────────────────────────────────────┘
┌─ 过程层（归档，不承担权威）────────────────────────────────┐
│  ⑤ 拍板档/推演图/票/开放项记录 → .archive/                 │
└────────────────────────────────────────────────────────┘
```

**与旧版（已作废）的关键差异**：

| 项 | 旧版（作废） | **新版（本文）** |
|:--|:--|:--|
| spec 的地位 | 长期存在、**域内权威** | **一次性实施文档**，关闭 effort 即作废 |
| 长期权威 | arch ＋ **各域 spec** | arch ＋ 领域文档 ＋ **需求文档**（spec 不在其中） |
| 取代关系 | 需要在旧 spec 头部标「已废弃」 | **不需要**——spec 整体作废，不产生取代场景 |

## 二、三类长期文档的职责边界

| 类 | 回答什么 | 落点 | 判据 |
|:--|:--|:--|:--|
| **arch 总纲** | 系统各部分**怎么相连** | `docs/architecture.md` | **横向**——涉及 ≥2 域的连接、边界、时序、依赖边 |
| **领域文档** | 本域内部**怎么定义/怎么算** | `docs/<域>schema.md` 等 | **垂直**——单域内的键清单、取值、算法、格式、DDL |
| **需求文档** | **用户要什么**（新增类） | `docs/需求.md`（待定名） | 用户故事、Problem、Solution、**验收与测法**、**范围外** |

**横/纵判据（你 2026-09-27 定的）**：

> 「具体放到 arch 是横向的内容，还是领域内的垂直的细化就要判断了。」

【我的推断】落成一句话：**回答「系统各部分怎么相连」→ 横向 → arch；回答「本域内部怎么定义/怎么算」→ 垂直 → 领域文档。**

**注**：同一条 spec 节**常同时含横纵两部分**（如 §4.12 既有横向的「分卷层外移」、又有纵向的「键清单」），故归宿行允许指向多处。

**DDL 归属（你 2026-09-27 定的）**：

> 「ddl 就应当是领域模型的一部分。」

即 **DDL 进领域文档**，不进 arch。

## 三、spec 的「五类归宿」（spec 作废前的分流规则）

【文档已写明】你 2026-09-27 逐条裁定：

| # | spec 内容 | 归宿 |
|:--|:--|:--|
| **1** | 测试决策（接缝/门禁/为什么这么测） | → **需求文档**（附「验收与测法」节） |
| **2** | Out of Scope（明确不做什么） | → **需求文档**（附「范围外」节） |
| **3** | 实现细节 | → **docs**（横向→arch／垂直→领域文档，见 §二判据） |
| **4** | 数据底座 DDL | → **领域文档**（DDL 是领域模型的一部分） |
| **5** | 开放项回填记录等过程物 | → **归档**（`.archive/`） |

**「归宿行」机制（本方案的完成标准）**：

> **spec 每节必须有一行「归宿行」**，取值只能四种：
> `→ arch §X` ／ `→ docs/<file> §Y` ／ `→ 需求文档 §Z` ／ `→ archive（过程物）`
> **「更新完成」＝ 每节都有归宿行，且指向的目标确实存在。**

**作用**：**语义判断仍做一次**（不可免），但**完成与否可机械判定**（查「每节有归宿行 + 目标存在」，不需读懂内容），**且它同时就是「spec 可否作废」的凭据**。

## 四、保留结论：长期文档之间的取代惯例（原版第 4 条，新方案下仍成立）

【文档已写明】你在原版讨论中提出并被 arch §12 采纳的一条：

> 「我不认为双状态机定稿是整体的 arch 文档，不应当取代 v1.0-design 而是仅作为状态机这个横切的能力层的权威。」

【实测】该判断已落地：`docs/architecture.md` §12「文档地图」把 `双状态机设计定稿.md` 归「**决策历史**」层，`v1.0-design.md` 归「**产品设计**」层且标注「部分过时、这几章仍有效」。

**新方案下的意义**：**长期文档之间「就地更新 + 修订史留痕」，不另起一份取代。** 【实测】三份领域 schema 文档（总纲/卷纲/弧纲）`status` 全为 `active`，**无一份处于被取代状态**——现行惯例就是就地更新。

**推论**：正因为长期文档之间不产生取代场景，**「取代声明」这个机制在长期层不需要**（这正是你裁定原拍板项 1、2「已无意义」的依据）。

## 五、生效前提：修正四份领域文档的「真相源」反置

**这是新方案能否成立的硬前提。**

【实测】四份 schema 文档现在都把 **spec 声明为「真相源」**：

| 文档 | 头部「真相源」原文（节选） |
|:--|:--|
| `docs/总纲schema.md` | **真相源**：`spec.md` **§4.12**（键清单正本…） |
| `docs/卷纲schema.md` | **真相源**：`spec.md` §4.1/§4.5/§4.7 |
| `docs/弧纲schema.md` | **真相源**：`spec.md` §4.1/§4.4/§4.7 |
| `docs/章级战略件schema.md` | **真相源**：`.plan/待拍板-大纲优化采纳-20260919.md` |

**问题**：**长期权威指向了临时文档**。spec 一作废，这四份文档的权威依据**全部悬空**。

**修法（方向反转）**：
- 领域文档**自身即权威**（它是领域模型的现行事实）；
- 保留 spec 指针但**改称谓**：从「**真相源**」改为「**决策来源**」（记「为什么这么定」，spec 归档后指向归档路径）。

# 01 协议落「文档分层」条款

## 交付什么

在 `plan-protocol` §三「文档形态约定」新增**文档分层**条款，把长期权威三层、一次性层、过程层的**职责边界**写成可检索的成文规则。

## 为什么需要

本 spec 的决策 1、2、3、6 目前只存在于 `.plan/doc-authority/spec.md` —— 而 spec 是**一次性文档**，按本方案自身规则最终要作废。**若不落协议，这四条决策随 spec 一起消失。**

## 具体内容

| 来源决策 | 要写进协议的内容 |
|:--|:--|
| 决策 1 | 五层两类生命周期：长期权威（arch 总纲／领域文档／需求文档）、一次性层（spec）、过程层（归档） |
| 决策 2 | 需求文档：新文档类 `type: requirements`；落点 `docs/requirements/<effort>-<主题>.md`；**文件名必须含 effort slug** |
| 决策 3 | 横/纵判据：回答「系统各部分怎么相连」→ arch；回答「本域内部怎么定义/怎么算」→ 领域文档；**DDL 归领域文档** |
| 决策 6 | 长期权威自指：长期文档**自身即权威**；不得把 spec 声明为「真相源」；对 spec 的指针改称「**决策来源**」 |

## 锚点（写在哪）

`plan-protocol` §三「文档形态约定」——与既有「状态头四字段」「`type` 取值约定」「`blocked_by` 格式」同节，紧邻编号。

## 依赖说明

**无前置**。本票是纯文本条款落定，不依赖任何其他票。

## 验收标准（外部可观察）

1. 读协议 §三，**能回答「这条新内容该写哪里」**——且答案唯一；
2. `docs/requirements/` 命名规则可**从文件名反查 effort 目录**；
3. 协议中不存在「long-lived 文档指向 spec 为真相源」这类反置表述；
4. `plan-lint` 通过（新增条款不得破坏既有校验）；
5. **skill 分发双拷贝 md5 一致**（`install-skills.sh` 执行后复核）。

## 诚实边界

本票**只写协议条款**，不建立 `docs/architecture.md`（本仓实测无该文件，仅有 `CONTEXT.md`），也不改动 novel 侧任何文档——用户已定「不是现在实施」（决策 9）。

# 待拍板：plan view 加载性能优化方案（2026-09-30）

## 用户原话（照抄）

> 现在 plan 的view 页面展示加载非常慢，这个有办法优化么？感觉速度如果今天重构前是 1 现在是 20

## 语境

- 本文档 = 排查结论 + 优化方案候选，等拍板选型后才动代码。

## 诊断结论（全部为本机隔离实例实测，非推断）

实测环境：planview-test profile 隔离实例（:3499，已清理），被测代码与主实例 ：3080 完全同源（harness `477b4f4` + better-sidebar 0.22.1）；主实例未做任何写操作，测试结束已恢复 `workspaceFence: true` 并停掉实例。

### 事实链

1. **数据量不是问题**：本仓 `.scratch`（6 effort）+ `.plan`（37 根层条目）共 86 个 md、<1MB；nvwa 仓同样小（1 effort、79 md）。
2. **单次 fs 调用 ~100ms**：`fs.tree`/`fs.read` 对任何目标（存在/不存在、热/冷会话）均 90–150ms；对照 `session.cwd`（纯内存）0.7–1.6ms、静态路由 ~1ms。本机裸 node 同路径 `realpath` 0.01ms。
3. **调用完全串行**：24 个并发 fs.tree 墙钟 2289ms（≈24×95ms），`Promise.all` 前端并行完全无效；总时长 = 调用数 × ~100ms。
4. **端到端复测**：按 `loadPlanMerged` 真实调用序列模拟（106 个 HTTP 调用），墙钟 **10.95s**——与用户体感量级吻合。
5. **进程采样（macOS sample）**：fs 请求期间主线程 91% 时间在做深度递归 StructuredClone 反序列化（`ValueDeserializer::ReadJSObjectProperties`），压 `session.cwd` 与空闲期均无此风暴。上游微机制（谁在 fs 路径上跨线程搬大对象）**未完全钉死**，属「我的推断」层：与 better-sidebar 0.22.x 新增的每调用 `ensureWorkspacePath`（两次无缓存 `realpath`，fence 关闭也照跑）及请求路径新增机制同期出现。
6. **归属核证（机制归属）**：
   - **票15 不是慢因**：diff 对照证明白名单化反而**减少**了 fs.tree 调用（重构前对 effort 下全部子目录各发一请求，含 assets/）。
   - **真正的变量是 better-sidebar 升级**：profile 内 0.19.1 → **0.22.1**（09-29 22:25 安装，pnpm store 两版本并存），主实例 09-30 02:42 冷启动后加载新版本。每调用 ~100ms 是 0.22.x 引入的传输层成本。
   - 昨晚另有 `session.cwd` 挂死修复（`8ecb415`，今日 00:21）：`sessionCwd` 现走 session/list 优先 + 10s 超时帽；session/list 实测 ~150ms 且 items 自带 cwd，当前非主要开销。
   - 「重构前=1」的基线实际是 better-sidebar 升级前的构建（每调用毫秒级），非票15 前后对比。

### 慢的算式

```
加载时长 ≈ fs 调用数(106) × 单调用成本(~100ms, 完全串行) ≈ 10.6s
```

调用数由视图读取契约决定（票15 已尽量收窄）；单调用成本由 better-sidebar 0.22.x 决定（上游侧）。

## 候选方案与影响

### 方案A（推荐）：dsh-plan-view 自建服务端 snapshot 路由

**边界澄清（2026-09-30 用户问「是不是接侧边栏、绕开 better-sidebar」）**：
- **解耦程度口径（现状盘点）**：tab 挂载已解耦（官方协议）；**读、写、cwd 兜底三类调用仍依赖 better-sidebar**——读 = fsTree/fsRead 16 个调用点（加载时展开成 106 请求，即慢的主因）、写 = fsWrite 1 处（`PlanView.tsx:933` 派活回写）、cwd 兜底 = `session.cwd` 路由（主路径 harness session/list 已解耦，fallback 保留 10s 帽）。方案A落地后读通道解耦；**写通道搬不搬是拍板子项**：一并搬（snapshot 体系加一个 write 端点，约几行）＝数据面对 better-sidebar 零依赖，其升版波动（如本次 0.22.x 变慢）伤不到 plan view；保留走它＝少动一处但留一根依赖线。助手推荐一并搬。
- **侧边栏接入完全不变**：Plan tab 挂载走的是 DSH 官方协议（`sidebarRightTabs.register` + `sidebar.right.pane.tab` slot，昨日已迁移），与 better-sidebar 无关，方案A不碰这层。
- **不是替换/绕开 better-sidebar 插件**：它照常运行（文件树、终端、其他插件照旧）。方案A只把 plan view 的**读文件数据通道**从「106 次 fetch better-sidebar 的通用 fs 路由」换成「1 次 fetch 本插件自己的专用路由」。
- **写操作仍走 better-sidebar**：派活回写 session 绑定（`PlanView.tsx:933` fsWrite，全插件唯一写点）低频单次，100ms 无感，不动。
- **server 半区骨架已在**：`package.json main` 已指 `lib/server.js`、`cordis.patch.yml` 已声明 server 条目，现为空壳（`apply()` 无行为）——方案A只是让这个空壳长出一条路由，不是新造结构。

- **做什么**：插件新增 server 半区，经 `ctx.webServer.register` 挂一条 `/plan-view/snapshot` 路由：入参仅 sessionId，服务端解析 cwd（`ctx.sessions.get`，进程内即时），按现行读取契约（map/spec 判据、白名单七目录、qa whitelist）在进程内直读 fs，**一次请求**返回全部树+文件内容；客户端 `loadPlanMerged` 改走该路由，解析/分类逻辑不动。
- **收益**：106 调用 → 1 调用，加载 ~10.9s → **~0.2–0.5s**；顺带消除 `sessionCwd` 往返与 10s 超时帽这一整类断点；不依赖 better-sidebar 版本行为。
- **影响面/成本**：本插件首次引入 server 代码（新面，manifest 加 server 入口）；响应体 ~600KB（可 gzip）；改码后须重建 lib + 冷启动 DSH web 生效（既定纪律）。围栏：路径全部由服务端从 session cwd 派生，天然在 workspace 内。
- **风险**：上游 better-sidebar 后续若改 session 面需跟；读取契约逻辑从客户端搬到服务端时须同步迁移对应注释契约（plan-protocol 关联）。
- **落地后剩余面（2026-09-30 补，答「A 做完还剩什么」）**：
  - **对 better-sidebar 剩零**（按推荐口径：snapshot 响应含 cwd/efforts/票文/全局台账/全局 qa/**rounds 清单**/**CONTEXT.md 正文**——rounds 与 CONTEXT 现也走 better-sidebar fs，须并入；写端点一并提供；sessionCwd 链整体退役，cwd 从 snapshot 响应取）。
  - **保留的全是 DSH 官方面**（协议依赖，非 better-sidebar）：`sidebarRightTabs`/slots（tab 挂载）、`sidebarRight.openResource`（打开票面文件）、input-bridge（宿主 setDraft）、`/api` 网关（session/list 活跃徽标、session/create 派单开票，走官方网关与 better-sidebar 无关）。
  - **性能剩余**：首屏 1 请求 ~0.2–0.5s；session/list ~150ms 并行不阻塞首屏；大 spec 正文渲染发生在打开子页时（非首屏）。
  - **A 管不到的**：better-sidebar 0.22.x 慢调用同样拖慢其他界面（侧栏文件树、编辑器、终端面板等）——属方案B（上游修复/核证）范畴，本票不含。
  - **工程尾巴**：读取契约逻辑迁移＋注释契约随迁；rounds/CONTEXT 并入响应；api.ts 清退 fsTree/fsRead/sessionCwd（fsWrite 视拍板子项）；单测更新＋snapshot 路由测试；planview-test profile 冷启动实测；重建 lib。

### 方案B：上游 better-sidebar 加批量路由或 realpath 缓存

- **做什么**：在 better-sidebar 0.22.x 加 `fs.batch`/snapshot 路由，或给 `resolveRealPath` 加缓存；发版后两 profile 升级。
- **收益**：同样 1 调用；**同时修复所有插件**的 fs 慢（不止 plan view）。
- **影响面/成本**：跨仓（DSH-better-sidebar）+ 发版 + 升级流程，周期长；需上游配合核证克隆风暴微机制。
- **风险**：上游侧改动归属不在本仓，短期内无法落地。

### 方案C：客户端调用数再压缩（叠加项，非解）

- 复用 subMaps 已取的 effort 树（省 6 次）、跳过确定无 spec 的 effort 的 spec 读取、正文惰性按需读。106 → ~60 调用 ≈ 6s。仍秒级，不达标；可在方案A落地后作为锦上添花。

### 方案D：客户端缓存/SWR（叠加项）

- 二次打开走缓存秒开，首次打开仍 ~10s；不解决主诉。

## 推荐

**方案A**（本仓自包含、一次调用、顺带消灭 sessionCwd 断点类），C/D 可作为后续叠加；B 作为上游问题另立机制归属核证记录（含本次采样证据），不阻塞本仓。

## 1. 这件事在讨论什么（语境）

### 1.1 上游：ZCode 侧已有一道硬门禁，现在要搬到 DSH 侧

昨天（2026-09-17）在 **ZCode**（另一家的编码代理命令行）里已经落地了一道「检索路由硬门禁」，正本记录在 `~/.zcode/docs/zg-硬门禁-hook-拍板.md`。它做的事是：

- 你先装了一个叫 **zg（zvec-grep）** 的本地检索服务，它给代理提供两种检索工具：一种是**精确查找**（等同于原来的 grep/rg，但不用建索引），一种是**语义检索**（按意思找，需要先建索引）。
- 但代理有惯性，老是顺手用老的 `grep`/`rg` 命令，不调用 zg。光在 AGENTS.md 里写「请优先用 zg」这种**软性偏好**已经证明没用（昨天就复发过一次）。
- 所以昨天在 ZCode 里加了一道 **hook（钩子）**：代理每次要执行命令前，钩子先检查命令内容，发现是裸的 `grep`/`rg` 就**直接拦下**（拒绝执行），并回一段中文说明，告诉它「请改用 zg 工具」。这就是「硬闸」。
- 同时还有第二道闸：代理要向子代理派活时，派活的文本里必须包含 zg 的用法说明，否则也拦。

**ZCode 侧的这套已经跑通并实测有效**。你这句话的意思是：**把这套机制在 DSH 侧也加上**。

### 1.2 为什么 ZCode 的配置不能直接抄（关键差异）

这是本次讨论的核心，必须说清：

| 项目 | ZCode 侧（昨天的做法） | DSH 侧（本次要做） |
|---|---|---|
| 硬闸装在哪 | 改 `~/.zcode/cli/config.json`，钩子脚本放 `~/.zcode/hooks/zg-gate.mjs` | **不能照抄**：DSH 没有这个配置文件 |
| DSH 的钩子怎么装 | — | DSH 用的是「桥接插件」：`~/.dsh/profiles/web/cordis.patch.yml` 里挂了一个 `@deepseek-ai/dsh-hooks-claude-code`，它去读一个 `hooks.json`。**当前那个 hooks.json 只配了 UserPromptSubmit 一个事件**，没有 PreToolUse |
| 拦什么 | 命令文本 `tool_input.command`（Bash 命令） | DSH 里抓取工具**根本没有 Bash 命令**一说，它是 `Grep` / `Glob` / `Read` 三个独立工具。所以要拦的是 `tool_name === 'Grep'`，看的是参数里的 `pattern`，**判定逻辑与 ZCode 侧完全不同** |
| 生效时机 | 改完新会话生效 | **同样**：钩子配置是会话启动时读取的快照，改完要新会话/重启才生效 |

**一句话**：机制思路可以照搬，**代码一行都不能复用**，要在 DSH 侧新写一个钩子脚本 + 改一份 hooks.json 挂载。

### 1.3 你说的「拦截 index」——我按三种理解都实测了，结论不同

你原话最后一句是「并再加一个拦截 index」。这句话有歧义，我实测了三件事来定它到底指什么，**请你确认是哪一种**（三种可以并存，不是互斥）：

**理解 A：拦截「对没建索引的仓库做语义检索」** —— 证据最支持这一条。

- 我实测：zg 的语义检索工具 `zvec_grep_search` 必须传一个 `root` 参数指向仓库路径，**如果那个仓库没建索引，它会自己现场建索引**。这不是猜测：`nvwa` 仓库的索引此刻状态就是 `◐ Workspace index is updating　4,648 个文件新增中`——也就是说**有人/某次调用刚刚触发了一次全量重建**。
- 一个 200 万字级的语料仓库现场建索引，代价是几分钟到几十分钟的算力，而且会占满嵌入模型。DSH 的默认超时只有 60 秒，所以实际结果是「卡住 + 超时 + 白烧算力」，比不拦更糟。
- 你的既有规矩里本来就有一条：**「建/重建/删索引须用户拍板」**。所以「没索引就拦下，提示去找你拍板」这条与你既有裁决**完全一致**，只是从口头规矩升级为机制拦截。

**理解 B：拦截「检索请求的 root 指向 nvwa」** —— 你原话括号里确实写了这个。

- 但这条**与事实不符**：我逐仓库实测了 zg 的精确检索（`zg query --rg`），在 `nvwa`、`novel`、`dsh-flow`、`deepseek-harness`、`semantica` 五个仓库**全部正常返回结果**，没有报错、没有拒绝。
- 所以我**没有找到任何事实依据**支持「要专门拦 nvwa」。**这一条我标注为：文档有空白 + 我的推断** —— 我推断你原话是想说「**举例说明**一个 root 参数长什么样的调用」，而不是「nvwa 这个仓库要被特殊对待」。**请你确认**，如果真是要专门封 nvwa，请说明原因（我猜不到动机，而这会封掉你 300 位作者技法库的主力检索仓库，代价很大）。

**理解 C：拦截「ng 索引管理命令」** —— 即拦住 `zg index`（建索引/删索引）这类命令。

- 这条与理解 A 是**同一枚硬币的两面**：A 拦「隐式触发建索引」（检索时被动发生），C 拦「显式调用建索引命令」。
- 两条一起上才算完整闭环：否则只拦 A，代理可以绕道直接调 `zg index` 去建，一样绕过你的「须拍板」规矩。

## 5. 方案与影响（每个选项说清代价）

### 方案对比：DSH 侧这道闸怎么装

**方案一（推荐）：新增一个 DSH 钩子脚本，挂在现有桥接上**

- 怎么做：在 `/Users/huzilin/workdir/dsh-plugin/packages/` 下新增一个小包（比如 `dsh-zg-gate`），里面一个脚本 + 一份 hooks.json；然后改 `cordis.patch.yml` 里的 `configPath` 指向新的 hooks.json（或者把两个 hooks.json 合并成一个）。
- 优点：改的是插件仓库（`dsh-plugin`），**不碰 DSH 主仓库源码**；与现有汇报规范钩子同构，以后好维护；可以在同一个脚本里同时实现「zg 调用门禁」和「index 门禁」。
- 代价：要新写约 80–120 行脚本 + 单测（照 ZCode 侧那套的标准）；改完**要重启 DSH 才生效**（钩子是启动快照）。

**方案二：直接改现有那份 hooks.json，往里塞 PreToolUse**

- 优点：文件更少。
- 代价：那份 hooks.json 属于「汇报规范钩子」这个包，把检索门禁塞进去会让两个不相干的关注点耦合在一个包；日后单独停用其中一个很麻烦。
- 结论：**不推荐**，除非你不在乎耦合。

**方案三：不装钩子，只写提示词**

- 结论：**已被证明不够**。ZCode 侧昨天就是这么做的，结果当天就复发。不列为可行方案，只为完整性列出。

### 关于第 4 节那个冲突点（重要）

你的「响应协议」里有一条硬性要求：**收尾检查阶段要无条件做域一致性 grep**（确认改名/术语变更后全仓库没有残留旧叫法）。

如果 DSH 侧也照 ZCode 那样「看到 `Grep` 工具就拦，逼你改用 zg」，那么这条协议就会**被自己的门禁卡住**——因为收尾校验恰恰需要在全仓库跑确定性文本检索，而 zg 的精确检索模式有两处行为差异（不支持 `-l`/`-c`；隐藏目录需显式开启），做「清零校验」时一旦出现假阴性，等于**校验通过但其实没查干净**，比不查更危险。

**所以这两件事必须分开裁决**，不能一起拍。三种处置：

- **处置甲（推荐）**：本次**只做 zg 门禁与 index 门禁，不拦 `Grep`**。`Grep` 保持原样，响应协议的收尾校验不受影响。ZCode 侧那套「拦裸 grep」的做法**不搬**，因为两个 harness 的工具形态不同，机械照搬反而制造假阴性风险。
- **处置乙**：拦 `Grep`，但**留一个显式的逃生口**（比如参数里带特定标记就放行），并把响应协议的收尾校验条款相应改成「走逃生口」。
- **处置丙**：拦 `Grep`，同时**先实测 zg 精确检索在「清零校验」场景下是否与 rg 等价**（覆盖隐藏目录、`-l`/`-c` 替代方案），确认等价后再上，否则不上。

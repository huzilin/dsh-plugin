> **一句话回答**：**你说得对，我上一轮说明页画错了两处**（把 grilling 画成单程、把 to-tickets 挂在 plan-approve 后面）。而且你发现的缺口是真的——**执行中发现的问题现在有三个落点，但没有一个是"票"**。

## 一、先认账：我说明页画错的两个地方

### 错 1：grilling 被我画成单程，实际是**循环**

我画的：`grilling → to-approval → plan-approve → to-tickets`（一路向前）

**你说的实际**：

```
grilling ⇄ plan-approve      ← 一轮一轮循环
    ↓
（拷问结束、决策收敛）
    ↓
回到主流程
```

**即 `plan-approve` 不是终点，是「一轮的结算点」**：结算完若还有没问透的，继续 grilling 下一轮；全收敛了才回主流程。**这个修正我接受**——它更符合 grilling 的原设计（按 frontier 一轮轮推进，直到 frontier 空）。

### 错 2：`to-tickets` 不该挂在 `plan-approve` 后面

**你的怀疑成立，实测支持**：

| 依据 | 实测 |
|:--|:--|
| `to-tickets` 的输入是 **spec** | `ideation-fe` 每票写着 `Source spec: .plan/ideation-fe/spec.md`；`wbflow-impl` 顶部写「把 `.plan/wbflow-impl/spec.md` **拆成 17 张**」 |
| `plan-approve` 手里**只有拍板结论** | 它读的是 `status: pending` 的决策文档，产出是「录结论 + 推进状态」 |

**硬把它们接起来 = 让票失去 spec 这个上游锚点**——票会变成「依据一句结论拆出来的」，没有需求文档可回溯。

**所以正常流程里，`to-tickets` 的前置永远是 spec，不是 plan-approve。**

**所以分类已就位，缺的是「结论要干活时如何生成票」这一步。**

## 三、两条流程的对照（我的梳理）

| | **主流程**（计划内的活） | **外部流程**（执行中冒出来的活） |
|:--|:--|:--|
| **起点** | 一个需求/想法 | 执行、测试、联调中发现的 bug / 断链 |
| **上游依据** | **spec**（`to-spec` 产出） | **？** ← **缺的就是这个** |
| **拆票** | `to-tickets`（吃 spec） | `to-tickets` **吃不了**（没有 spec） |
| **决策** | 讨论中直接定 | `to-approval`（`origin: review`）→ 你拍板 |
| **执行** | `implement-spec` / `implement` | 同上 |
| **回写** | `plan-sync` / 执行时当场翻 | 同上 |

**缺口定位**：外部流程缺的是 **「从问题到可执行单元」之间的那段依据**——主流程有 spec 承担，外部流程没有。

## 四、外部流程该怎么走（三个方案）

### 方案 A：轻量 issue 文档（推荐）

**做法**：执行中发现的问题，按 `to-approval` 落成待拍板文档（`origin: review`）；**若拍板结论是「要修」，就地补一份轻量 `issue.md`**（几行：现象 / 根因 / 期望行为 / 验收标准），它充当这份外部工作的「**迷你 spec**」，然后 `to-tickets` 吃它拆票。

| | |
|:--|:--|
| 好处 | 票仍有上游依据（可回溯）；复用现有 `to-approval` 与 `to-tickets`；不新增 skill |
| 代价 | 多一份小文档；要定「issue.md 长什么样」 |
| 落点 | `.plan/<effort>/issues/<NN>-<slug>.md` |

### 方案 B：允许「无 spec 的轻量票」

**做法**：给 `to-tickets` 加一条例外——**外部流程的票可以不挂 spec，但必须在票内自述背景**（现象/根因/验收），即把 spec 的内容内联进票。

| | |
|:--|:--|
| 好处 | 少一份文档 |
| 代价 | 票变重；且**失去"上游依据"这一层**——多个票共享的根因分析无处安放（方案 A 的 issue.md 正好承担这个） |

### 方案 C：并入现有台账，不生成票

**做法**：外部问题只记 `acceptance-issues.md`，修的时候不开票，当场修。

| | |
|:--|:--|
| 好处 | 最轻 |
| 代价 | **回到"看不见"的老问题**——台账不是票，插件读不到，进度不可见；且无验收勾选可追踪 |

## 五、我推荐 A，理由

1. **保住「票必有上游」这条原则**——主流程靠 spec，外部流程靠 issue.md，**两条链结构同构**，只是上游文档不同；
2. **根因分析有地方放**——一个 bug 常拆出多张票（如「断链」可能牵出 3 处修），共享的根因写在 issue.md 里，票各自引用，**不重复**；
3. **不新增 skill**——`to-approval` 与 `to-tickets` 都已存在，只是补一条「外部流程用它俩」的走法；
4. **可回溯**——票的 `Source spec:` 那行改指 issue.md，链条完整。

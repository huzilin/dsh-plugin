# doc-authority · 需求文档（spec 一次性化与文档权威治理）

> **本文职能**：本需求（`.scratch/doc-authority/`）的**长期权威落点**——写「用户要什么」。承载用户故事、Problem、Solution、验收与测法、范围外。
>
> **来源**：`.scratch/doc-authority/spec.md` 定稿时按五类归宿分流至此（决策 4：①测试决策→需求文档②Out of Scope→需求文档）。
>
> **本文件名含 effort slug `doc-authority`**，故可从本文反查 `.scratch/doc-authority/` 目录。

## Problem（要解决什么）

`.plan/` 里的 spec 在 effort 关闭后仍留在仓里，与 `docs/` 下的长期文档**同时自称有效**。同一片领域被多张 effort 先后触碰时，新旧两份 spec 结论不一致，而**后续会话读到哪一份是随机的**——它会照旧 spec 实现，把已被取代的方案重新引入。

实测规模：novel 仓 **66 处文档冲突（30 处高危）**，实现工单最密集（21 处，且**验收清单已全部打勾、打勾的是旧口径**）。

历轮整治的动作是「给旧文档补废弃标记」，但标记**写在了 agent 读不到的位置**：30 份带标记文档中仅 7 处可机械检索（**23%**），标记位置从全文 5% 到 88% 不等，最差两份埋在 84%/88% 处——而 agent 先读头部。更严重的是旧文档头部仍保留「**可交付实现直接照做**」这类**主动邀请照做**的权威宣告，与后补的过时声明互相打架。

上游 `to-spec` / `implement` 对「废弃/取代」**零覆盖**——写 spec 时不读旧 spec、不声明取代了谁；动手时不检查目标是否失效。**事件发生在「agent 读到旧权威那一刻」，而没有任何环节在那时设卡。**

**用户视角**：我花多轮整治废弃标记，但下次仍然用废弃方案；我不确定这套方案本身是不是有积弊。

## Solution（要什么）

**让 spec 退化为一次性实施文档，让 `docs/` 成为唯一长期权威。**

- **spec 随 effort 生命周期**：effort 关闭后 spec **整体作废**并归档，不再作为长期权威存在；
- **作废前做一次分流**：按五类归宿把内容分别并入 arch 正本、领域文档、需求文档，过程物归档；
- **`docs/` 三类长期文档**：arch 总纲（横向·系统各部分怎么相连）、领域文档（垂直·本域内怎么定义/怎么算）、**需求文档**（用户要什么）；
- **归宿行作为完成标准**：spec 每节须有一行归宿行；「更新完成」＝每节都有归宿行且指向的目标存在。

**为什么这能根治**：现行问题的根源是「多份文档同时自称有效」。spec 一次性化后**冲突的对象消失了**——长期权威只有 `docs/` 一套，spec 是通往它的脚手架。**「废弃标注」这个需求本身随之消失**（用户 2026-09-27 据此裁定原「废弃声明上头部」「取代关系可检索」两项已无意义）。

## 用户故事

1. 作为协议维护者，我希望 spec 有明确的生命周期终点（effort 关闭即作废），以便它不再与长期文档争夺权威。
2. 作为协议维护者，我希望 spec 作废前有一次确定的分流动作，以便其中仍有价值的内容不会随作废丢失。
3. 作为协议维护者，我希望分流结果可机械校验（每节有归宿行、目标存在），以便「更新完成」不依赖主观判断。
4. 作为协议维护者，我希望长期文档分为三类且职责边界清晰，以便新内容知道该写到哪里。
5. 作为协议维护者，我希望有一条可操作的判据区分「横向内容进 arch」与「垂直内容进领域文档」，以便归置时不必反复讨论。
6. 作为协议维护者，我希望 DDL 明确归入领域文档，以便数据模型不被拆到两处。
7. 作为协议维护者，我希望需求文档承载用户故事、Problem、Solution、验收与测法、范围外，以便「用户要什么」有独立落点。
8. 作为协议维护者，我希望需求文档的**文件名包含 effort 名字**，以便从需求文档能直接定位它是哪一摊工作产生的。
9. 作为协议维护者，我希望长期文档**自身即权威**、不得把 spec 声明为「真相源」，以便 spec 作废时不会连带废掉长期文档的权威依据。
10. 作为协议维护者，我希望对 spec 的指针改称为「决策来源」，以便读者知道那记的是「为什么这么定」而非「现在是什么」。
11. 作为实施会话（agent），我希望在动手前能查到目标文档是否已失效，以便不照废弃方案实现。
12. 作为实施会话（agent），我希望读到失效文档时被要求先读新正本并在票面留痕，以便事后可复盘是否执行过。
13. 作为收口会话，我希望 spec 定稿时就把 docs 更新到最新，以便不依赖「关闭 effort 后」那个上下文已散的时刻。
14. 作为收口会话，我希望重新拍板影响既有结论时同步更新 docs，以便测试/评审环节产生的口径变更不悬空。
15. 作为新仓的 init 会话，我希望协议已写明这套分层，以便不必重新发明、也不再重演「多份文档并存」。
16. 作为项目接手者，我希望从 arch 拿到整体关系、从领域文档拿到本域细则、从需求文档拿到用户诉求，以便三处各有其职、不互相污染。
17. 作为协议维护者，我希望票型词表里只有真正合法的值（`impl` 不在其中），以便不会再有会话写出不被识别的票。
18. 作为协议维护者，我希望 `blocked_by` 只有一种写法且两侧指向同一正本，以便不再出现「协议写一套、wayfinder 写一套」。
19. 作为协议维护者，我希望 status 字段的归属有定论，以便决定是撤回扩展还是把它写进契约。
20. 作为协议维护者，我希望票态终态只有一个词（`done`），且 `done` 与 `out_of_scope` 严格区分，以便阻塞计算不被静默破坏。

## 验收与测法

**被测对象是协议条款，不是运行代码**——故测试形态为**条款可执行性核验**，而非单元测试。

**什么算好测试**：只验**外部可观察的结果**——即「另一会话读到协议后，能否照条款走完流程」，不验协议措辞本身。

| # | 被测面 | 判据 |
|:--|:--|:--|
| 1 | **归宿行可机械校验** | 取一份真实 spec，检查「每节有归宿行、目标存在」能否被脚本判定（不需读懂内容） |
| 2 | **spec 作废凭据成立** | 归宿行齐全 ⇒ 可作废；缺失 ⇒ 不可作废 |
| 3 | **五类归宿分流可执行** | 取一份 spec 试分流，检查五类是否都有明确落点、无「无处可去」项 |
| 4 | **横/纵判据可判定** | 取若干节，检查按判据能否得到唯一归宿（多归宿是否只发生在「确实横纵兼有」时） |
| 5 | **需求文档命名可关联** | 检查「文件名含 effort slug」是否足以从需求文档反查 effort 目录 |
| 6 | **票态词表单向** | `resolved` 是否被 lint 拦截（探针实测：已验） |
| 7 | **阻塞区分不被破坏** | `out_of_scope` 票 + 依赖它的票，依赖票**必须仍显示阻塞** |

**先例**：novel 仓有 `D-17` 互验口径（`architecture.md` 与代码零漂移）与 `D-11` 文档标注口径，可作「文档域条款核验」的形态先例。

**不测什么**：不测协议文风优劣（那是评审事项）；不测 novel 存量文档的当前正确性（本方案不实施该改动）。

**测法汇总节（归本文件）**：上游 spec 模板的 `## Testing Decisions` 节整节归宿于此。

## 范围外

- **对 novel 仓库的任何实际改动**——7 份 spec 的作废、4 份领域 schema 的「真相源」反置修正，均**不在本方案范围**（用户已定「不是现在实施」）；
- **用批量替换解决术语残留**——已被实测推翻（旧词「强制定稿」非归档区现存 141 处、仅 34 处带合法留痕，且 2026-09-27 仍在被新写入），不进本方案；
- **`plan-lint` 新增归宿行门禁**——本次不新增机械校验（归宿行的脚本校验待协议落地后另议）；
- **effort 边界与 scope 机制**（destination 锁 scope、图分裂）——独立议题。

**曾不在范围、后经拍板转入范围的三项**：

| 项 | 变化 | 依据 |
|:--|:--|:--|
| 票型词表 `impl` 清理 | → 在范围且**已实施** | 用户裁定「不必支持 impl，并清理协议中的这个 type」 |
| `blocked_by` 格式统一 | → 在范围且**已实施** | 用户裁定「统一 block 的格式，plan-protocol 和 wayfinder 保持一致」 |
| status 与协议全局对齐 | → 在范围且**已实施** | 用户裁定「是和 plan-protocol 对齐，内部保持一致」「全局一致，不兼容 wayfinder」 |

**仍不在范围**：对 novel 侧文档的实际改动。

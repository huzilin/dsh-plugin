# to-qa-testcases（构建测例）

本 skill 只做**构建测例**一件事：设计依据盘点 → 用例设计（六组）→ 可执行资产三原则。产物 = `.plan/<effort>/qa/cases.md`（无 effort 的项目按其 docs 惯例放 `qa/cases.md`）+ 仓库 `qa/` 下可执行资产（环境一键重建 + 驱动一键复跑 + 结果可对比）。 无图归属的回测测例（SOP 回测 / 整页回测，挂不到具体工单/图）落 `.plan/qa/cases-<主题>.md`，进 plan 第一层「测例&缺陷」tab。 cases.md 落盘后给**被测票** frontmatter 回写 `qa_cases: true`（票卡「🧪 测例」徽标的数据源；后续 `qa_tested`/`qa_accepted` 由 run-qa-testcases 写）。**不执行测例、不出验收结论、不登缺陷**——那半截在 `run-qa-testcases`（跑测例 → 验收记录 → 缺陷台账 → 返工闭环）。

> **标准权威说明**：本 skill 承载《用例设计》cases.md 章节骨架与资产三原则的**权威版本**（正文见 `references/testsuite-skeleton.md`）。项目内若有同名模板（如 `qa-acceptance-template.md`），以本 skill 为准，模板退役或改为指针。
> **分工**：`run-qa-testcases` 管执行与缺陷（本 skill 产出的测例集与资产就是它的执行武器，验收记录/缺陷台账骨架也在它的 references/）；`diagnosing-bugs` 管失败用例根因定位；测试场景协议层（造数禁令/验收五维 DoD/真模型 E2E/替身语义）5 个正本在 `run-qa-testcases/references/`，造数前必读 `run-qa-testcases/references/data-construction.md`。

## 为什么存在（设计门禁原理）

测试全绿仍被用户发现问题，绝大多数不是执行不认真，而是**测试设计依据（oracle）不全或通道单一**——用例写得再好，也只能验证「设计者想到的预期」。常规自检 checklist 只查用例写得好不好，从不查预期来源全不全。本 skill 把「预期来源全不全」变成写用例前的第一道门：用例设计必须从盘点开始，不从模仿开始。

已知盲区分六类（B1 oracle 缺源 / B2 通道单一 / B3 断言停在协议层 / B4 文档-实现漂移 / B5 验证环境≠用户验收环境 / B6 共享夹具耦合），定义、信号与真实案例见 `references/case-library.md`。**新教训只往案例库追加，不改本文**；只有出现新类型时才回来补防线。

## 设计依据盘点（开跑前准出，缺源不得开跑）

列出本次测试的全部预期来源，逐源标注「已列入 / 不适用（写明原因）/ 缺失（补齐后才开跑）」，原样写进 cases.md §1：

1. **spec 的 AC**（`.plan/<effort>/spec.md`）；
2. **spec 全文行为性明文**——不只 AC 章：状态机行、联动条款、「X 时必须 Y」句式逐条抽成行为清单。AC 章之外的明文要求最容易整类漏测；
3. **契约真相源**（api proto / openapi）；
4. **原型 / mockup / 设计稿**——凡有 UI 的需求必列，逐页面、逐元素、逐交互形态；没有这个源，「实现 vs 应有形态」的差距整类不可见；
5. **架构正本与设计定稿**（架构唯一正本如 `docs/architecture.md`；项目自有的设计定稿），且须与裁决正本互验，防文档过期；
6. **用户历史批注/反馈原话**——本项目全部历史批注逐条转 oracle。用户说过一次的要求，第二次仍漏测是最不可接受的盲区；
7. **live 数据 / seed / 真实环境**；
8. **环境与数据纪律**——自动化资产锚定的数据对象来源合法性：必须为本测例集自建（前缀自命名），显式排除他人存量造数与验收专用数据（**无写路径≠可消费**）；「**验收环境适配**」自查：本 effort 是否需要用户验收环境的存量数据支撑，需要则声明数据获取方式与构建脚本；并发场景写明隔离与清理手段（头部声明三件套：维度 + 数据集唯一 id + 构建脚本路径，见骨架 §二）。

然后做**双向映射**：每个源条目 ↔ 用例编号。任一条目无对应用例 = 设计缺口，补齐或显式声明降险后才算设计完成。

## 断言三维（每个功能点过三层，只测第一层等于没测业务）

1. **协议层**：接口按契约返回——正常/拦截/幂等/负路径；
2. **业务语义层**：每个角色在这一步**业务上需要什么**（评审者要看到被评审产物；用户进详情页要知道需求说什么；状态改了看板分类要变）。落地手法 = **写读联动 sweep**：每个写路径列出全部下游读方，逐一断言（这是「域一致性 grep」的测试版）；
3. **呈现层**：页面实际渲染什么——布局分区、元素在位、默认态（展开/折叠）、视觉编码（颜色/徽标表达的状态语义）。

## 双通道（定义）

- **协议通道**：API/DB 黑盒驱动 + 库态对账；
- **呈现通道**：浏览器真实走查（有 FE 必走）——开首页看第一眼、点完整条用户旅程、全程截图对照原型。

**红线：纯协议通道不得对 UI 出「通过」结论。** 两通道结果同权重进验收结论。用例设计必须覆盖两条通道的断言；**执行、截图记录与「用户验收环境数据巡检」归 `run-qa-testcases`**。

## 依赖（输入）

| 输入 | 何时有 / 用于什么 |
|---|---|
| `spec`（`.plan/<effort>/spec.md`）的 AC | AC → 验收用例逐条映射（B/C 组主骨架） |
| spec / 架构文档全文 | 抽「行为性明文」清单（状态机、联动条款、「X 时必须 Y」）——**不只 AC 章** |
| 契约真相源（api proto / openapi） | A 组接口专项：每接口正常/拦截/幂等/负路径 |
| 架构正本（`docs/architecture.md`）与设计定稿 | 接口口径、数据可测性、边界态说明 → 联调场景与数据构造 |
| 原型 / mockup / 设计稿 | 呈现层断言 + 原型逐条 diff（有 UI 必给，缺失即 gap-naming） |
| 页面源码 / 设计稿 / 词汇表 | P 组文案逐字断言的 oracle（源码里的占位/空态/提示条字符串即预期值） |
| 用户历史批注 / 反馈原话 | 逐条转回归用例（长期保留在回归范围） |
| 代码 / MR / featureBranch + 环境凭据 | 资产构建（测试环境、驱动脚本）与库态对账 |

## Focus（上游必读 → 产出到哪）

| 上游来源 | 必读内容 | 产出到 cases.md |
|---|---|---|
| spec AC | 每条 AC 的通过/不通过判据 | §2 覆盖矩阵「覆盖的 AC」列（B/C 组主骨架） |
| spec 行为性明文 | 状态迁移、跨表联动、通知触发 | B 组断言维度（含跨层联动 sweep） |
| 契约 | 每端点入参/出参/错误码 | A 组（每接口至少 1 正 1 负 1 幂等） |
| 架构正本 | 数据可测性、边界态、序列化口径 | §4 联调场景与数据构造；资产 env/seed |
| 原型 | 页面骨架、元素在位、默认态、交互形态 | **P 组**（逐页面 diff 清单） |
| 页面源码 | 文案字符串、空态文案、字段位置与排布 | **P 组**（P-1 位置/文案逐字/形态/空态；P-2 操作/反馈/持久化/失败回滚/降级） |
| 用户批注 | 原话 | 「用户批注回归组」（编号 U-xx） |

## Process

1. **设计依据盘点（强制第一道门）**：按上文「设计依据盘点」完成八源清单 + 双向映射；缺源未补齐或未显式降险 → 不进入第 2 步。把盘点结果原样写进 cases.md §1「设计依据清单」。

2. **用例设计（cases.md）**：按调用形态落用例（默认全量六组；纯页面验收形态按骨架「纯页面验收形态」精简骨架节），每条唯一编号 `组-序号`，预期结果可判定（禁「功能正常」）：
   - **A 接口/单元专项**：每端点/每函数 ≥ 1 正常 + 1 拦截/负路径 + 1 幂等/重放；
   - **B 主流程走查**：全节点/全路径走通，每步过**断言三维**（协议层：返回与状态机；业务语义层：该角色此步业务上需要的东西已到位 + 写路径的全部下游读方；呈现层：页面渲染/默认态/视觉编码）；
   - **P 页面预期验收（有 UI 必设；单列成组，不得并入 B 组）**：B 组管「链走得通」，P 组管「页面看起来对不对（UI）、用起来对不对（使用）」——两组并列、互不替代，B 组全绿不代表 P 组绿。**全呈现腿，不得以协议腿代出「通过」**；每条设计上即预留截图位。内部两表分列，逐元素位过一遍：
     - **P-1 UI 呈现**：位置（在页面哪一处、与相邻元素同排不换行不重叠）/ 文案逐字（标签、占位、空态、浮层、提示条——错一字即 ✗）/ 形态（字号层级、色彩系、默认态与选中态、视觉编码）/ 空态 / 长列表不撑破布局；
     - **P-2 使用交互**：操作可达 / 反馈（立即回显 + 提示条文案与类型，不刷新页面）/ 持久化（刷新后仍生效）/ 失败路径（中文可读 + **乐观更新须回滚到库真值**）/ 降级语义（辅助功能失败不阻断主流程且提示可见）/ 起点正确（弹窗打开时预选=该对象当前值，可改可清）/ 文案正交 sweep。
     - 准出：每元素位 ≥ 1 条 P-1 + 1 条 P-2，且该元素位的失败/降级路径必有一条。维度表与表格结构见骨架 §2/§3。
   - **C 分支剧本**：AC 逐条 + 异常/边界/权限/空数据/并发竞速/重复提交/通知投影；
   - **D 对账**：库态直查（产物矩阵、审计 append-only、计数对账）+ **用户验收环境数据合规巡检**（对用户实际浏览的库跑同一套期望矩阵，隔离环境全绿不替代）+ **文档-实现一致性**（设计文档 vs 裁决正本 vs 实现）。D-3/D-4 的**用例在此设计**；执行侧巡检出结论归 `run-qa-testcases`；
   - **U 用户批注回归**：历史批注原话逐条一用例。
   完成 cases.md §5 设计自检后才算设计完成。

3. **测试资产（三原则，缺一不算完成）**：
   - **数据可一键重建**：并发隔离按**维度**不按库——不要求每测例集独立库/命名空间，按被测业务域选定**并发控制维度**（电商域=商品、写作域=书），同环境并行的各测例集各占不同维度值；**cases.md §0 头部声明三件套，缺一不达标**：①并发控制维度是什么（如：书）；②数据集唯一 id=具体实例（书 id/书名；id 运行时生成的由构建脚本产出后回写登记位、头部登记当前实例，禁只报 `-<ts>` 模式不给实例）；③构建该数据集的自动化脚本路径（一键重建）。测试内容=§2/§3 用例集。数据可一键重建（迁移 + seed，维度值被污染即重建自愈），凭据经环境变量注入零落地，`env_up` / `env_down` 成对；机器资源（端口/工作目录/容器与进程名）自命名零共享带测例集标识（独库为维度取「环境」的可选实现）+ 临时工作目录显式声明（**禁 /tmp**），红线见骨架 §二「并发与环境红线」；造数纪律（真实接口链路构造、禁 SQL 直插业务表、造不到=SKIP）见 `run-qa-testcases/references/data-construction.md`，建 seed 前必读；
   - **脚本可一键复跑**：驱动脚本**软失败收全**（单条断言失败不中断，一轮收齐全部缺陷）、结果落 json、退出码 FAIL>0 非 0 可接 CI；等待一律条件探测（探测间隔+上限+早退，**禁固定死等做就绪判定**），红线见骨架 §二「等待与确定性红线」；代码路径 + 驱动入口 + 用例编号绑定按 cases.md §0「测试代码」行声明（三项缺一不达标，见骨架 §0）；
   - **结果可对比**：定义基线口径 `PASS / FAIL / SKIP`，SKIP 必附因。
   资产随需求入库；**下一轮不重写数据与脚本**。
   > 有 UI 的项目：呈现通道可执行资产以 **Playwright 形态**为标准（spec 落 `qa/e2e/`、用例编号 grep 绑定、薄壳驱动、截图/登录约定 + 无视觉降级口径），正本见 [references/playwright-assets.md](references/playwright-assets.md)；P 组设计时按其探针口径把呈现层断言写成可判定的文本断言。

4. **落盘 + 自检**：cases.md 与资产落盘（`.plan/<effort>/qa/cases.md` + 仓库 `qa/`）→ 按本 skill「自检」逐条过 → 按项目产物登记惯例登记 cases.md 与资产 link。执行、验收记录、缺陷登记交 `run-qa-testcases`。

## 调用形态（自然语言触发语，非 CLI 参数）

| 调用 | 形态 | 行为差异 |
|---|---|---|
| 「写用例 / 设计用例 / 建测例资产」（默认） | **全量六组** | 上文 Process 全标准：八源盘点、六组用例、资产三原则 |
| 「纯页面验收用例 / 只要 P 组 / 出页面走查清单」 | **纯页面验收** | 按骨架「纯页面验收形态」精简骨架：只 P 组呈现腿 + 人工走查定位链（核心产出）；免协议六组与协议资产；数据三件套与造数纪律不减 |

新增形态先在此表登记行为差异再进 Process，不在对话里临时裁剪。

## 自检（完成前逐条过，任一 blocker 不过不许交出测例集）

> 按全量六组形态逐条过；纯页面验收形态按骨架「纯页面验收形态」节的减免表处置资产类条目，红线类条目（数据三件套、定位链、P 组维度）不减。

- [ ] （blocker）八源盘点与双向映射已写入 cases.md §1，无未处置缺源
- [ ] （blocker）spec 全部 AC 在 cases.md §2 覆盖矩阵有对应用例编号，无空行
- [ ] （blocker）每条用例唯一编号、预期可判定（无「功能正常」）；cases.md §5 设计自检全过
- [ ] （blocker）资产三原则齐备：env_up/env_down、驱动脚本（软失败 + json + 退出码）、基线 PASS/FAIL/SKIP 口径已定义；cases.md §0「测试代码」行声明齐备（代码路径 + 驱动入口 + 用例编号绑定）
- [ ] （blocker）脚本等待全部条件探测（探测间隔 + 上限 + 早退，超时即红），无固定死等做就绪判定（红线见骨架 §二）
- [ ] （blocker）并发与环境红线达标：头部声明三件套齐备且可复核——①并发控制维度 ②数据集唯一 id（具体实例 id/书名，非 `<ts>` 模式）③构建脚本路径（均在 cases.md §0，红线见骨架 §二「并发与环境红线」）；机器资源自命名零共享（端口/工作目录带测例集标识，资源清单入 README）、临时工作目录显式声明且非 /tmp、env_up/env_down 构建与清理步骤成文（红线见骨架 §二「并发与环境红线」）
- [ ] （blocker）有 UI 则 **P 组已单列**（每元素位 ≥1 条 P-1 + 1 条 P-2，含失败/降级路径）+ 逐页面对齐原型；无 UI 须显式声明
- [ ] （blocker）涉人工查看数据的用例定位链单独成列、不与测试内容混写——顶层对象《切换器可找到的名》→子对象《名+树中位置》→目标对象《可搜索特征》，零 id 定位、无「同卡/承上文」链式引用、纯页框行填「不依赖业务数据」（红线见骨架 §3「人工走查定位链」）；纯页面验收形态按精简骨架产出且数据三件套照旧
- [ ] （major）B 组每步断言含业务语义层（角色所需 + 写读联动），非仅协议层
- [ ] （major）P 组文案类断言逐字可判定（占位/空态/提示条原文入预期栏），非「文案合理」
- [ ] （major）gap-naming：缺料处写「证据缺失：待补 X」，未编造预期或数据

## 边界 / Out of scope

- 不生成需求或 AC——需求与 AC 的生成不属本 skill；AC 缺失走 gap-naming 并批注，不自造验收口径。
- **不执行测例、不出验收结论、不做缺陷登记与返工闭环**（`run-qa-testcases` 的活）；本 skill 只保证测例集可执行、可复跑、可对比。
- 不定位根因、不修 bug（`diagnosing-bugs`）；执行中发现的缺陷按 `run-qa-testcases` 骨架登记后再交接。
- 不替代用户验收：用户验收节点保留，本 skill 目标是把「呈现/语义类」问题在执行前就排进断言。
- 不做性能/安全专项（另立专项）。

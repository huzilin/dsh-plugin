# 测试数据构造纪律（造数禁令）

> 测试与验收数据的构造纪律：真实链路构造、禁伪造、造不到如实 SKIP。

## 禁令（普适，命令级）

**一切测试/验收/演示数据，必须通过被测系统的真实接口链路逐步构造，禁止 SQL 直插业务表伪造状态。**

## 细则

1. **API 链路造不到的状态 = 如实标注 SKIP**（注明替身/环境不可达的原因 + 由哪条单测覆盖该状态），**宁缺毋假**——宁可少一个预置状态，绝不伪造（假数据让验收结论变假阳性，且污染统计与埋点）。
2. **环境清理（DELETE）不算数据构造**，可用 SQL；但必须在脚本中与构造部分严格分离并注释。
3. 造数必须**脚本化留存**（仓库内脚本，如 `scripts/seed_*.py`）：可复跑、每步打印响应证据、SKIP 显式可见；禁止临时手搓 SQL。
4. **触发条件（按动作特征判定，不按任务自称）**：凡要向数据库/环境写入任何状态以供人查看或验收——无论任务自称开发/数据准备/QA/修数——开工前先读本纪律。任务命名与实际活动不符正是违规常见根因，不得以「这不是测试任务」豁免。
5. **单条数据自检**：每条写入前自问——「这个状态，用户在真实界面上手动操作能造出来吗？」不能 = 伪造 = 禁；改走 API 链路或显式标注 SKIP。
6. 对替身环境的推论：替身造不到的状态恰恰是「替身覆盖边界」的真实信息，应上报而不是抹平；如需让替身可达（如可配置 findings），走代码变更（替身能力增强），不走数据伪造。

## 演示数据真实性

- 造数/演示数据要求语义真实，避免出现「两个相同版本」式的困惑观感（如提交落版与修复落版出现雷同占位文案）。
- 提交类动作的演示应保持正文不变（全对齐无 diff），修复产出用 config 可配的拟真文（如 fake_revise_text），数据仍走真实链路落库而非伪造。

## 违规实例复盘

部分数据行 SQL 直插漏网 → 用户巡检发现来源徽标假阳性。根因：任务被归类为「数据准备」而非「QA 活动」，本纪律未被触发；且修症状不修根因（只修被点名的链路，同类入口仍假）——凡违规复盘必须查同族入口。

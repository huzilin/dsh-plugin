## 一、《执行验收记录》`.plan/<effort>/qa/test.md`

> 落点：`.plan/<effort>/qa/test.md`。**本文件不加 frontmatter 状态头**——qa 三件套中只有 `defect.md` 加头（裁定⑧），本文件保持纯正文形态，不被 plan 视图识别。

### §0 基本信息

### §1 测试概述与结论（结论先行）
**验收结论**：[通过 / 有条件通过 / 不通过] —— [一句话理由]
- 末轮结果：PASS n / FAIL n / SKIP n（SKIP 逐条附因）
- 遗留：S1/P0 n、S2/P1 n（编号指向 defect.md）

### §2 覆盖与执行结果 + 过程有效性

|---|---|---|

|---|---|---|---|---|

### §4 AC 逐条核对（三态，无缺项）
| 功能/模块 | AC | 执行用例 | 结果（通过 / 不通过 / 未覆盖） | 说明 |

### §5 回归指引（下次重测操作卡）
```
1. 重置环境：<env_up 命令>
2. 运行回归：<驱动命令>            # 基线 PASS n / FAIL n / SKIP n

## 二、《缺陷台账》`.plan/<effort>/qa/defect.md`

> 落点：`.plan/<effort>/qa/defect.md`（一个 effort 一个台账文件）。

### 文档状态头（2026-09-20 裁定⑧：只有缺陷加头，必须是真 frontmatter）

首行 `---` 开、闭合 `---`。**不写 ```yaml 围栏、不写引用块**——围栏/引用块插件读不到（实测三种旧写法全不合规）：

```
---
type: qa-defect
date: <YYYY-MM-DD>
status: <五态之一>
origin: <readability-rescue / proactive / review / retrospective>
---
```

- `type` 固定 `qa-defect`（plan-protocol `type` 取值约定已登记）；
- `status` 用 plan-protocol 既有五态：`pending` / `closed` / `superseded-by:<path>` / `active` / `abandoned`——**不新造词表**。缺陷全关闭写 `closed`，仍有未关闭写 `active`；
- `cases.md` 与 `test.md` **不加头**，不被 plan 视图识别（插件 qa 组按 `type: qa-defect` 白名单）。

### 清单总览（首节，表头全项目统一，逐字不得改列）
| 缺陷号 | 标题 | 严重度 | 类型（rd/fe/arch/docs） | assignee | 状态 | 关联用例 | 发现源 | 测试设计缺口 |
|---|---|---|---|---|---|---|---|---|

- **类型**：条目级字段，值域 `rd` / `fe` / `arch` / `docs`（既有 role_id，**不用 backend/frontend**），取代旧 `domain` 列（避免双真相源）；
- **状态**：六词 `新建 / 已确认 / 修复中 / 待复测 / 已关闭 / 挂起` **照用，允许附注**（如「已关闭（复测 PASS）」「已拍板关闭（最小原则，非缺陷）」）——插件解析**取首词**匹配（按 `[\s(#:—-]` 切首词），附注写在首词之后；
- **发现源**：`QA 轮` / `用户`；**测试设计缺口**：用户渠道必填（缺哪个源/维度/通道），缺口当轮补进 cases.md（教训反哺，事件追加 `to-qa-testcases/references/case-library.md`）。

### 每条缺陷（A~E 五节，E 必填）

**A. 基本信息**：缺陷编号 / 标题 / 发现人 / 发现日期 / 所属版本 / 模块 / 指派 / 相关需求-用例 / 严重程度（S1 严重 / S2 一般 / S3 轻微 / S4 建议）/ 优先级（P0~P3）/ **环境信息**（库 + 服务 + commit）。

**B. 缺陷详情**：缺陷描述 / 复现步骤（编号）/ 预期结果 / **实际结果（原样报文或截图，非转述）** / 根因定位（如已知，代码级 file:line）/ 附注。

**C. 返工与复验记录**：状态（六词 + 允许附注，见上）/ 原因分类（程序错误 / 需求变更 / 需求缺失 / 设计缺陷 / 环境 / 数据）/ 修复方案 / **复测口径（= E 节命令翻绿 + 回归基线数）** / 复测结果 / 关闭人-日期。
> 诊断方（diagnosing-bugs）修复后只回写本节。

**D. 归属判定**：**类型**（`rd` / `fe` / `arch` / `docs`，与总览表「类型」列同值）+ 判定理由（证据：哪层的成因）。

**E. 最小复现入口（diagnosing-bugs Phase 1 交接，必填）**
| 字段 | 值 |
|---|---|
| cmd | [一条命令：驱动脚本 + 用例过滤，如 `python3 qa/qa_diag_min.py --case B-5g`] |
| 环境变量 | [名称清单；值经 env_up 注入，不落地] |
| 前置 | [env_up 命令 / seed] |
| 末次运行输出 | [redacted 关键行，须为红] |
| 复现率 | [100% 确定性 / 竞速类：循环 N 次命中 M] |
| 预期绿信号 | [修复后该命令的通过判据] |

### 发现源统计（复盘视图，末节）
| 发现源 | 条数 | 类型（业务语义 / 呈现 / 判据 / 口径 / 竞速 / 文档） | 对应设计缺口 → 已补用例 |
|---|---|---|---|
> 用户渠道条数 > 0 时，逐条回写缺口并追加到 `to-qa-testcases/references/case-library.md`（归入既有盲区类型；案例库维护纪律见 to-qa-testcases）。

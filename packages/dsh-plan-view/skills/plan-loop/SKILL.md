# plan-loop（收口循环）

本 skill 是 plan 生态的**循环驱动器**：不发明任何单据格式与状态词，只按 `plan-protocol` skill（公共协议层）的形态契约与交接契约，把 `.plan/` 里既有单据一轮轮推到终态。三条流程、票面词表、台账恢复口径、缺陷状态机，均以 `plan-protocol` skill 为准。

**单据**（本 skill 的统一对象词，即循环的推进对象）：`.plan/` 下四类带状态的文档——工单（`tickets/<NN>-*.md`，状态读 frontmatter `status`）、缺陷（`qa/DEF-NN-*.md`，读 `- 状态:` 字段行）、测例（`qa/cases.md`，推进方式 = 执行并回写票面 qa 标记）、挂账台账（两级 `ledger/`，读 `- 状态:` 字段行）。审批文档（`待拍板-*.md`）**不是单据、不推进**——要人工决策；循环只在收尾呈报，拍板后产生的新单据由下一轮盘点自然接住。

**右推纪律（第一约束）**：循环期间不停下等确认、不逐项提问。凡需用户拍板的动作——选型分叉、收图判定、归档时点、证据不足的翻面——记入本轮**裁决单**，循环继续推其余可执行项。仅两种情况允许提前停：不可逆的破坏性操作；剩余单据已全部处于待拍板或终态。收尾一次交付 Brief 与裁决单，用户逐行回批（如「A1 批；B 全批；C2 选 C」），回批项由下一轮落地。

## 每轮五步

**每轮从第 1 步重新盘点，禁止沿用上一轮清单**——上一轮的推进本身会产生新单据（修复产生缺陷档、回批产生票、实施暴露新挂账），缓存清单就是漏单。

### 1. 盘点

扫全 `.plan/`（`handoffs/` 与 `.archive/` 不属 plan 生态，跳过），枚举四类单据并按上面的读取口径取状态，分三桶：

- **可执行**：下一步明确且在 agent 权限内（第 3 步动作表有对应行）
- **待拍板**：卡在选型分叉的单据、缺陷暴露的需求级分歧
- **已终态**：票 `done` / `resolved`、缺陷 `已关闭`、台账 `已销` / `已转票`——本轮跳过

同时扫 `待拍板-*.md`（状态头 `pending` / `active`）逐档记一行卡点：不进桶、不推进，收尾呈报。盘点后先跑 plan-lint（脚本随 plan 系 skill 安装，在本 skill `scripts/` 下），形态违例先修复再推进。

### 2. 排序

可执行桶按默认优先级：可启动挂账（启动条件已触发）> 未关闭缺陷（阻塞 qa_accepted）> 实施图前沿票（`blocked_by` 全终态的 `open` 票）> 未执行测例（票全 done 未验收的图）> 推演图未清决策（`open` 的 research / prototype / grilling 票）。

### 3. 推进

逐项执行，动作按单据类型对表：

| 单据 | 触发状态 | 动作 | 终态 |
|---|---|---|---|
| 工单 | `open` 且 `blocked_by` 全终态 | 先执行登记（`claimed` + `claimed_by` + `session`，格式见 `plan-protocol` skill），再按 `implement` skill（实施图）或对应推演 skill（推演图）执行；验收框逐条勾，附 diff/commit 翻面 | `done` / `resolved` |
| 工单 | `blocked_by` 有未终态 | 本轮跳过；依赖票翻面后自然进前沿 | — |
| 缺陷 | 待修复 / 已确认 / 修复中 / 待复测 | 按 `diagnosing-bugs` skill 修复（`待复测` 态则跳过修复直接复测；只回写 DEF 的 C 节），回 `run-qa-testcases` skill 同命令复测翻绿 | `已关闭` |
| 缺陷 | 暴露需求级分歧 | 转 `to-approval` skill 立审批档，进待拍板桶 | — |
| 测例 | 图内票全 done 但 `qa_accepted` 未齐 | 按 `run-qa-testcases` skill 跑该图：全绿给被测票写 `qa_accepted`；有缺陷立 DEF-NN 进修复环 | 票面 `qa_accepted: true` |
| 台账 | `可启动` 且启动条件已满足 | 按**恢复口径**转票（恢复到来源图立票，`- 状态:` 改 `已转票` 并留痕；原图 closed 则重开） | `已转票` |
| 台账 | `可启动` 但启动条件未触发 | 不硬开工；能补启动条件就补，不能的保持等待态、简报列明 | 等待态（非终态） |
| 台账 | 债务已被客观证据清偿 | 在条目自身销账并注记（日期 / 去向 / 证据）；拿不准的进裁决单 | `已销` |
| map | 实施图达收口条件（全票 done + qa_accepted + 无未关闭缺陷） | 提名收图、不自行翻面，进裁决单确认组 | `closed`（回批后下轮翻） |

推进中产生的新单据**当轮入账**：按对应 skill 的形态落盘，进下一轮盘点。一张票一收口：翻面必附证据，做完即 commit，不攒批翻面、不读盘批量改状态。

### 4. 对账

按 `plan-sync` skill 口径回收「看起来已完成、票面没翻」的票。与本 skill 的唯一差分：证据强（代码与 commit 双证）当场翻面并留落地注记，不等确认；证据弱不翻，进裁决单列明缺什么。

### 5. 简报与裁决单

每轮收尾交付两样：

- **Brief**（会话消息交付）：每个未终态 effort 一行（图型 / 距终点差什么 / 卡点 / 下一步）；每条非终态台账一行（挂账-NN 带号 / 状态词 / 启动条件是否触发）；每条未关闭缺陷一行（DEF-NN / 状态 / 卡点）；每份 `pending` 审批档一行（路径 / 卡点，只呈报不代办）；本轮每项推进一行（单据 + commit 或票号）。
- **裁决单**（落盘 `.plan/待拍板-收口裁决单-round-<NNN>-<日期>.md`，状态头四字段、`status: pending`）：**确认组**（收图提名、归档提名、对账弱证据项）与**拍板组**（循环内冒出的选型分叉），每行给选项与影响，支持逐行回批。

裁决单的回批结论由下一轮落地（该立票的调 `to-tickets` skill）。`pending` 审批档的拍板归用户（走 `plan-approve` skill），拍板落出的新单据由下一轮盘点自然入账——循环不代办。

## 终止条件

一轮盘点后可执行桶为空，循环结束。剩余单据只会是三种：已终态、等待态（启动条件未触发的挂账、`挂起` 的缺陷——如实列明）、待拍板（裁决单已交）。实施图全灭（全票 done + qa_accepted + 无未关闭缺陷）、推演图决策清零、两级台账零在挂（或全部等待态），即全仓收口；此时在裁决单提名归档——归档归 `plan-archive` skill 且不自动跑。

## 防假推进红线

- 票面状态以 frontmatter 为准，不读正文表格。
- 一切状态翻转必附 diff 或 commit；没有证据的「已完成」就是没完成。
- 不可执行的挂账不硬开工：推进 = 补启动条件或按恢复口径转票。
- 执行登记不齐的票不许开工。
- 循环不拍板：审批文档不是推进对象，`plan-approve` 的结算只能由用户触发。

## 会话形态

用户喊一声（`/plan-loop` 或「跑收口循环」）点火一次，循环在本会话内连跑多轮直到终止条件。单据状态全在 `.plan` 文件里，天然可续：会话中断后重新点火，从第 1 步盘点续跑，不丢进度。参数可选：给 effort 名或单据号则只推该范围，缺省推全 `.plan/`。

## Problem Statement
> **归宿（2026-09-27）**：→ 需求文档 docs/requirements/doc-authority-文档权威治理.md §Problem

`.plan/` 体系里的 spec 在 effort 关闭后仍然留在仓里，与 `docs/` 下的长期文档（架构正本、领域 schema）**同时自称有效**。同一片领域被多张 effort 先后触碰时，新旧两份 spec 的结论会不一致，而**后续会话读到哪一份是随机的**——它会照旧 spec 实现，把已被取代的方案重新引入。这一现象在 novel 仓造成了 **66 处文档冲突（30 高危）**，其中实现工单最密集（21 处，且**验收清单已全部打勾、打勾的是旧口径**）。

历轮整治的动作是「给旧文档补废弃标记」，但实测发现标记**写在了 agent 读不到的位置**：30 份带标记的文档中仅 7 处可机械检索（23%），标记位置从全文 5% 到 88% 不等，最差的两份埋在 84%/88% 处——而 agent 读文档先读头部。更严重的是旧文档头部仍保留「可交付实现直接照做」这类**主动邀请照做**的权威宣告，与后补的过时声明互相打架。

同时，上游 mp 的 `to-spec` / `implement` 两个 skill 对「废弃/取代」**零覆盖**——写 spec 时不读旧 spec、不声明取代了谁；动手时不检查目标文档是否已失效。事件因此发生在「agent 读到旧权威那一刻」，而没有任何环节在那时设卡。

**用户视角的问题**：我花多轮整治废弃标记，但下次仍然会用废弃方案；我不确定这套方案本身是不是有积弊。

## Solution
> **归宿（2026-09-27）**：→ 需求文档 docs/requirements/doc-authority-文档权威治理.md §Solution

**让 spec 退化为一次性实施文档，让 `docs/` 成为唯一长期权威。**

- **spec 随 effort 生命周期**：effort 关闭后 spec **整体作废**并归档，不再作为长期权威存在；
- **作废前做一次分流**：按五类归宿把 spec 内容分别并入 arch 正本、领域文档、需求文档，过程物归档；
- **`docs/` 三类长期文档**：arch 总纲（横向·系统各部分怎么相连）、领域文档（垂直·本域内怎么定义/怎么算）、**需求文档**（用户要什么）；
- **归宿行作为完成标准**：spec 每节须有一行归宿行，四种取值之一；「更新完成」＝每节都有归宿行且指向的目标存在。

**为什么这能根治**：现行问题的根源是「多份文档同时自称有效」。spec 一次性化后，**冲突的对象消失了**——长期权威只有 `docs/` 一套，spec 是通往它的脚手架。**「废弃标注」这个需求本身随之消失**（用户 2026-09-27 据此裁定原「废弃声明上头部」「取代关系可检索」两项已无意义）。

**需求文档命名（用户 2026-09-27 敲定）**：文档名**必须包含 effort 的名字**，便于关联。命名形态见 §Implementation Decisions 决策 2。

## Implementation Decisions
> **归宿（2026-09-27）**：→ arch docs/architecture.md §二/§五（横向：三层结构与文档分层） ＋ 需求文档 §范围外（决策 9 范围边界） ＋ archive（决策过程与逐条裁定留痕）

**决策 1：文档分层（五层，两类生命周期）**

```
长期权威层（docs，持续维护、永不退役）
  ① arch 总纲      全仓唯一，写「系统是什么」
  ② 领域文档      每域一份，写「本域内怎么定义/怎么算」
  ③ 需求文档      写「用户要什么」
一次性层（随 effort 生命周期）
  ④ spec.md       写「这一批怎么做」；effort 关闭后作废并归档
过程层（归档，不承担权威）
  ⑤ 拍板档/推演图/票/开放项记录 → .archive/
```

**决策 2：需求文档命名（用户 2026-09-27 敲定：「名字要包含 effort 的名字，方便关联」）**

【文档已写明】用户原话：「需求文档这个名字敲定，并且文档名字要包含 effort 的名字，方便关联。」

- **类名（type 值）**：`requirements`
- **落点**：`docs/requirements/<effort>-<主题>.md`
- **命名规则**：**文件名必须含 effort slug**，形如 `<effort-slug>-<主题>.md`；同一 effort 可有多份（按主题拆），但**每份都带 effort slug**
- **关联依据**：effort slug 即 `.plan/<slug>/` 的目录名，故需求文档与 effort 目录**同名可检索**

示例（形态示意，非现行文件）：
- `.plan/outline-generation-chain/` → `docs/requirements/outline-generation-chain-大纲生成.md`
- `.plan/chronicle-review/` → `docs/requirements/chronicle-review-编年审核.md`

**决策 3：横/纵判据（用户 2026-09-27 定：「放到 arch 是横向的内容，还是领域内的垂直的细化就要判断了」）**

> **内容回答「系统各部分怎么相连」→ 横向 → arch；回答「本域内部怎么定义/怎么算」→ 垂直 → 领域文档。**

- 同一条 spec 节常同时含横纵两部分（如既有横向的「分卷层外移」、又有纵向的「键清单」），**故归宿行允许指向多处**；
- **DDL 归领域文档**（用户原话：「ddl 就应当是领域模型的一部分」）。

**决策 4：spec 五类归宿（用户 2026-09-27 逐条裁定）**

| # | spec 内容 | 归宿 |
|:--|:--|:--|
| 1 | 测试决策（接缝/门禁/为什么这么测） | → **需求文档**（附「验收与测法」节） |
| 2 | Out of Scope（明确不做什么） | → **需求文档**（附「范围外」节） |
| 3 | 实现细节 | → **docs**（横向→arch／垂直→领域文档） |
| 4 | 数据底座 DDL | → **领域文档** |
| 5 | 开放项回填记录等过程物 | → **归档**（`.archive/`） |

**决策 5：归宿行机制（完成标准）**

spec 每节须有一行归宿行，取值只能是四种之一：

```
→ arch §X
→ docs/<file> §Y
→ 需求文档 <path> §Z
→ archive（过程物）
```

**「更新完成」＝ spec 每节都有归宿行，且指向的目标确实存在。**

形态（写在该节标题下）：

```markdown
### 4.12 <节标题>
> **归宿（<YYYY-MM-DD>）**：→ arch §7.5 ＋ docs/<file> §3 ＋ 需求文档 <path> §2 ＋ archive（Problem/Solution）
```

**理由**：语义判断仍要做一次（不可免），但**完成与否由此可机械判定**（查「每节有归宿行 + 目标存在」），且**它同时就是「spec 可否作废」的凭据**。

**决策 6：长期权威自指（修正现状反置）**

【实测】四份领域 schema 文档现把 spec 声明为「**真相源**」（总纲/卷纲/弧纲 schema、章级战略件 schema）。**长期权威指向临时文档**——spec 一作废，其权威依据全部悬空。

规则：
- 长期文档**自身即权威**（它是现行事实）；
- 不得把 spec 声明为「真相源」；
- 对 spec 的指针**改称「决策来源」**（记「为什么这么定」；spec 归档后指针指向归档路径）。

**决策 7：协议条款清单（本 spec 的产出物）**

写进 `plan-protocol` §三「文档形态约定」的六条：

| # | 条款 | 内容 |
|:--|:--|:--|
| 1 | **文档分层** | 长期权威三层（arch／领域文档／需求文档）＋一次性层（spec）＋过程层（归档） |
| 2 | **需求文档** | 新增文档类；落点与命名规则（决策 2）；承载用户故事/Problem/Solution/验收与测法/范围外 |
| 3 | **spec 生命周期** | spec 随 effort 生命周期；关闭 effort 后作废并归档；作废前按五类归宿分流 |
| 4 | **归宿行** | 每节须有归宿行（四类取值）；「更新完成」＝每节有归宿行且目标存在 |
| 5 | **横/纵判据** | 横向→arch；垂直→领域文档；DDL 归领域文档 |
| 6 | **长期权威自指** | 长期文档自身即权威，不得把 spec 声明为「真相源」；对 spec 的指针称「决策来源」 |

**决策 8：设置读时检查（原拍板项 3，用户选 A）**

用户 2026-09-27 裁定：拍板项 3 **选 A**。

- `implement` / `implement-spec`：动手前**检查目标 spec 是否存在取代声明 / 是否已归档**；有则先读 docs 正本，并在票面留痕「**已核新正本：<path>**」；
- **定位**：这是**过渡期护栏**——spec 一次性化全面落地前，历史 spec 仍会被读到。

**决策 9：作用范围与时点**

【文档已写明】用户 2026-09-27：「我们现在是确定 plan 如何进行项目管理的方案，而不是实施方案。」「可以作为方案落协议，但不是现在实施。」

**决策 11：`blocked_by` 格式两侧统一（2026-09-27 裁定，已实施）**

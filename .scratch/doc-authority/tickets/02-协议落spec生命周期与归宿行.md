# 02 协议落「spec 生命周期与归宿行」条款

**Status:** resolved
**Blocked by:** None — can start immediately

## 交付什么

在 `plan-protocol` §三新增**spec 生命周期**与**归宿行**两条条款，让「spec 何时作废」「作废前内容去哪」「怎样算更新完成」三件事**可机械判定**。

## 为什么需要

这是「废弃方案复活」的**根治手段**。实测根因：旧文档仍在断言权威（「可交付实现直接照做」），且**读取时无任何门禁**，而作废标记散落在文件 5%~88% 位置——agent 先读头部，读到的是旧结论。归宿行把「内容已搬家」变成**头部可见、脚本可查**的事实。

## 具体内容

| 来源决策 | 要写进协议的内容 |
|:--|:--|
| 决策 3（生命周期） | spec 随 effort 生命周期；**关闭 effort 后作废并归档**；作废前按五类归宿分流 |
| 决策 4 | 五类归宿表：①测试决策→需求文档（验收与测法节）②Out of Scope→需求文档（范围外节）③实现细节→docs（横→arch／纵→领域文档）④DDL→领域文档 ⑤过程物→归档 |
| 决策 5 | **归宿行机制**：每节一行，四类取值（`→ arch §X` ／ `→ docs/<file> §Y` ／ `→ 需求文档 <path> §Z` ／ `→ archive（过程物）`）；**「更新完成」＝每节有归宿行且目标存在** |

## 锚点（写在哪）

`plan-protocol` §三「文档形态约定」。**建议紧随票 01 的分层条款**——归宿行的目标路径依赖分层定义，顺序颠倒会读不通。

## 依赖说明

**无阻塞依赖**（`blocked_by: []`），但**内容上承接票 01**：归宿行的四类取值需要先有「需求文档」「领域文档」的定义才可解析。**建议同批实施、01 在前**。

## 验收标准（外部可观察）

1. 取一份真实 spec，**脚本可判定**「每节有归宿行 + 目标存在」——不需读懂内容；
2. **作废凭据成立**：归宿行齐全 ⇒ 可作废；缺失 ⇒ 不可作废；
3. 五类归宿分流**取 `outline-generation-chain/spec.md` 试跑**，无「无处可去」项；
4. `plan-lint` 通过 + skill 分发 md5 一致。

## 诚实边界

- 本票**不新增 `plan-lint` 门禁**——归宿行的脚本校验属落地后另议事项（spec Out of Scope 已明示）；
- 本票**不动 novel 现存 7 份 spec**。
